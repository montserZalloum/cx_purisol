# Feature Specification: Notifications

**Feature Branch**: `006-notifications`
**Created**: 2026-04-18
**Status**: Draft
**Input**: User description: "Phase 6 — Notifications: proactive in-system alerts to the Purisol Administrator. Four distinct notification triggers — **Customer Low Stock** (after a Coupon Consumption Entry submit, when the affected customer's total remaining coupons across all their `Sold` non-`Depleted` booklets has reached or fallen below `Purisol Settings.customer_low_stock_threshold`); **New Discrepancy Opened** (after a `Purisol Coupon Discrepancy` record is inserted by Phase 5's detection logic); **Warehouse Low Stock** (after a Sales Invoice submit, when the count of `Purisol Coupon Booklet` records with status `In Stock` drops below `Purisol Settings.warehouse_low_stock_threshold` — deduplicated so it fires at most once per calendar day); and **Booklet Depleted** (emitted from the Coupon Consumption Entry's depletion logic when a booklet transitions to `Depleted` because its 20th coupon was just consumed). All four notifications are delivered through the ERPNext bell-icon notification channel (Notification Log) to every user holding the `Purisol Administrator` role. A single channel-agnostic utility — `Purisol Notify`, a plain Python module, not a DocType — is introduced with one public `send(recipient, subject, message, reference_doctype, reference_name)` function; every trigger in Phase 6 routes through this one function, so a later phase can add email / SMS / WhatsApp channels by editing the utility's internals without touching any trigger site. Thresholds are read fresh from `Purisol Settings` at each evaluation so administrators can edit them live without a deploy. Reports, dashboards, and any non-bell channel are out of scope."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Notify Administrator When a Discrepancy Is Opened (Priority: P1)

Every time Phase 5's detection logic inserts a new `Purisol Coupon Discrepancy` record — whether `Missing Coupons` or `Unassigned Booklet`, whether the triggering consumption entry created one discrepancy or five — the Administrator receives a bell-icon notification within the same transaction, one per discrepancy, each linking directly through to that discrepancy record. The notification's subject and body identify the discrepancy by name (`PCD-xxxx`), its type, the affected booklet (`WP-xxxxx`), and the delivery man who submitted the triggering consumption entry. Because Phase 5 already creates the discrepancy records silently, Phase 6 adds the layer that actually reaches the Administrator: a bell dot appears, they click it, and they land on the `Open` discrepancy ready to investigate. The notification is per-user — every user holding the `Purisol Administrator` role gets their own bell-icon entry — so the alert is not missed even if the primary Administrator is off-duty.

**Why this priority**: Discrepancies are the highest-risk events the system surfaces — they are literally the fraud / loss signals Phase 5 exists to produce. Without a notification, a discrepancy record can sit `Open` on the list view for days before anyone looks at it, defeating the whole purpose of automatic detection. P1 because this trigger is the single highest-value alert in Phase 6 — shop owners will judge the notification system on whether this one works. Also P1 because it is the trigger with zero dedup logic and no threshold configuration, so it is the simplest to ship; getting it working first proves the `Purisol Notify` abstraction end-to-end.

**Independent Test**: Can be fully tested by seeding one user with the `Purisol Administrator` role, one booklet `WP-00001` that is `Sold` with all 20 coupons `Available`, and then submitting a Coupon Consumption Entry that skips coupons (e.g. submits `CP-00007` when `CP-00001`–`CP-00006` are `Available`, so Phase 5 creates a `Missing Coupons` discrepancy). Verify exactly one new ERPNext Notification Log entry exists for the seeded user, with a subject referencing the newly-created discrepancy by name, a body mentioning the booklet `WP-00001` and the delivery man, and `document_type = "Purisol Coupon Discrepancy"` / `document_name = <new discrepancy name>` so clicking routes to the record.

**Acceptance Scenarios**:

1. **Given** one user with the `Purisol Administrator` role exists, **When** Phase 5's detection logic inserts a new `Purisol Coupon Discrepancy` (via Consumption Entry submit), **Then** exactly one ERPNext Notification Log entry is created with `for_user = <that user>`, `document_type = "Purisol Coupon Discrepancy"`, `document_name = <new discrepancy's name>`, and subject / body referencing the discrepancy's name, type, booklet, and triggering delivery man.
2. **Given** two users both hold the `Purisol Administrator` role, **When** a new discrepancy is inserted, **Then** two Notification Log entries are created — one per user — each with the same subject and reference but with its own `for_user`.
3. **Given** a single Consumption Entry submit causes Phase 5 to create three distinct discrepancies (e.g. two `Missing Coupons` across two booklets plus one `Unassigned Booklet`), **When** the submit completes, **Then** three separate Notification Log entries are created per administrator user — one per discrepancy — each linking to its own record.
4. **Given** no user currently holds the `Purisol Administrator` role, **When** a discrepancy is inserted, **Then** no Notification Log entries are created, no error is raised, and the discrepancy creation still succeeds (empty-recipient is a silent no-op).
5. **Given** a discrepancy is transitioned from `Open` to a `Resolved - *` state by the Administrator submitting it, **When** the resolution submit completes, **Then** no new notification is emitted — Phase 6 only notifies on discrepancy **creation** (`after_insert`), not on resolution.

### User Story 2 - Notify Administrator When a Customer Runs Low on Coupons (Priority: P1)

When a Coupon Consumption Entry is submitted, the system recomputes each affected customer's total remaining coupon count across all their currently-`Sold` (and not yet `Depleted`) booklets. For each unique customer touched by the entry whose total remaining has reached or fallen below `Purisol Settings.customer_low_stock_threshold`, a bell-icon notification goes to every user with the `Purisol Administrator` role — one notification per unique affected customer per Consumption Entry. The message names the customer and the current total (for example, "Customer Al-Masri Restaurant has 2 coupons remaining. Prepare a new booklet."), and the click-through leads to that Customer's record so the Administrator can start preparing the next sale. Phase 4's auto-depletion (transitioning a booklet to `Depleted` when its 20th coupon is consumed) has already run by the time this check fires, so `Depleted` booklets are correctly excluded from the "remaining" total. The threshold is read fresh from `Purisol Settings` at each evaluation, so administrators can edit it in the singleton form without a restart.

**Why this priority**: Customer low-stock notifications are what turn the Purisol system from a passive record-keeping app into an active revenue tool — the shop owner gets told who needs a new booklet, prompting the next sale. Same P1 tier as Story 1 because it is one of the two truly-proactive alerts the phase promises; Warehouse Low Stock and Booklet Depleted are also important but happen at lower frequency (stock runs out rarely; booklets deplete once per booklet lifecycle). Customer low-stock fires on essentially every busy day — it is the everyday utility of the whole notification subsystem.

**Independent Test**: Can be fully tested by (a) seeding one customer `C-AL-MASRI`, two booklets `WP-00001` and `WP-00002` both `Sold` to that customer with 2 and 1 coupons remaining respectively (total = 3), setting `Purisol Settings.customer_low_stock_threshold = 3`; (b) seeding one user with the `Purisol Administrator` role; (c) submitting a Coupon Consumption Entry that consumes one more coupon from `WP-00001` (new totals: 1 + 1 = 2, which is below threshold). Verify exactly one new Notification Log entry is created with `for_user = <the admin user>`, `document_type = "Customer"`, `document_name = "C-AL-MASRI"`, and a subject/body mentioning the customer name and remaining count of 2.

**Acceptance Scenarios**:

1. **Given** `Purisol Settings.customer_low_stock_threshold = 3` and customer `C-AL-MASRI` has total remaining = 4 across their Sold booklets, **When** a Coupon Consumption Entry is submitted that consumes one of their coupons (dropping total remaining to 3), **Then** exactly one Customer Low Stock Notification Log entry is created per administrator user, with `document_type = "Customer"`, `document_name = "C-AL-MASRI"`, and body naming the customer and the number 3.
2. **Given** a Consumption Entry consumes coupons from two different customers' booklets, both of whom end up at or below threshold, **When** the entry is submitted, **Then** two distinct Customer Low Stock notifications are created per administrator user — one per customer — each referencing its own customer record.
3. **Given** a customer is already below threshold (total remaining = 1), **When** a Consumption Entry consumes their last remaining coupon from a booklet that now depletes (booklet transitions to `Depleted`, customer total remaining = 0), **Then** a Customer Low Stock notification still fires with remaining count = 0 — a customer at zero is the strongest case for an immediate resale prompt.
4. **Given** a customer's total remaining is 10 and `customer_low_stock_threshold = 3`, **When** a Consumption Entry consumes one of their coupons (new total = 9, still above threshold), **Then** no Customer Low Stock notification fires for that customer.
5. **Given** a Consumption Entry touches a booklet that has no customer (an `Unassigned Booklet` case per Phase 5), **When** the entry is submitted, **Then** the customer-low-stock check skips that booklet entirely — there is no customer to evaluate — and no Customer Low Stock notification fires for the unassigned booklet (Phase 5 still creates its `Unassigned Booklet` discrepancy, which fires Story 1's notification separately).
6. **Given** the Administrator edits `customer_low_stock_threshold` from 3 to 5 on `Purisol Settings` at 10:00, **When** a Consumption Entry is submitted at 10:01 that leaves a customer at total remaining = 4, **Then** the Customer Low Stock notification fires using the new threshold of 5 — no caching delay, no restart required.

### User Story 3 - Notify Administrator When Warehouse Booklet Stock Runs Low (Priority: P2)

When a Sales Invoice is submitted that flips one or more booklets from `In Stock` / `In Custody` to `Sold` (via Phase 3's on-submit hook), the system counts how many `Purisol Coupon Booklet` records still have status `In Stock`. If that count has dropped strictly below `Purisol Settings.warehouse_low_stock_threshold`, a single bell-icon notification goes to every user with the `Purisol Administrator` role saying how many booklets remain and prompting a new generation batch. Because a busy sales day might submit several invoices in quick succession, all of which leave the warehouse below threshold, the notification is deduplicated to fire at most once per calendar day — once the Administrator has been told stock is low today, the system does not re-tell them on subsequent invoices the same day. The dedup resets at midnight (next calendar day the same condition fires fresh). Clicking the notification routes to the `Purisol Coupon Booklet` list view filtered to `In Stock`, so the Administrator can review remaining stock and decide whether to kick off Phase 1's booklet generation.

**Why this priority**: Warehouse low-stock alerts prevent operational paralysis — if the shop runs out of `In Stock` booklets during a sales day, customer sales cannot complete. But it is a lower-frequency trigger than Stories 1 and 2: discrepancies and customer low-stock fire on consumption activity (daily), whereas warehouse-low-stock fires only when a sale crosses a rarely-approached threshold and shop batches typically generate 20–50 booklets at a time (meaning the condition exists for a small window every few weeks). P2 because delaying this trigger does not break day-to-day operations — the `Booklets In Stock` number is also visible on the Phase 8 dashboard — but shipping it earns the Administrator a proactive safeguard they would otherwise have to watch for manually.

**Independent Test**: Can be fully tested by (a) setting `Purisol Settings.warehouse_low_stock_threshold = 5`, seeding six booklets with status `In Stock`, one customer, one administrator user; (b) selling one booklet to the customer via Phase 3's sales flow, which on submit should transition it to `Sold`, leaving five `In Stock` — still **not below** threshold, so no notification fires; (c) selling a second booklet, leaving four `In Stock` (below threshold); verify exactly one Warehouse Low Stock Notification Log entry is created per administrator user, referencing the count 4; (d) selling a third booklet the same day (three `In Stock`) — verify **no new notification** fires (dedup within the calendar day); (e) advancing the server date to the next day and selling a fourth booklet (two `In Stock`) — verify a fresh Warehouse Low Stock notification fires.

**Acceptance Scenarios**:

1. **Given** `Purisol Settings.warehouse_low_stock_threshold = 5` and exactly 5 booklets have status `In Stock`, **When** a Sales Invoice is submitted that transitions one of them to `Sold` (now 4 `In Stock`, which is below 5), **Then** exactly one Warehouse Low Stock Notification Log entry is created per administrator user with a body mentioning the count 4.
2. **Given** `warehouse_low_stock_threshold = 5` and 4 booklets are already `In Stock` (the condition has already been met earlier today, a notification has already fired today), **When** another Sales Invoice submit drops the count to 3, **Then** no new Warehouse Low Stock notification is created for that day — the existing daily dedup suppresses it.
3. **Given** a Warehouse Low Stock notification fired yesterday and the count has been below threshold continuously since, **When** a Sales Invoice is submitted today that does not change the fact of being below threshold, **Then** exactly one fresh Warehouse Low Stock notification fires today — the dedup resets at calendar-day boundaries.
4. **Given** `warehouse_low_stock_threshold = 5` and 6 booklets are `In Stock`, **When** a Sales Invoice is submitted that drops the count to 5 (exactly equal, not strictly below), **Then** no Warehouse Low Stock notification fires — the trigger is strict inequality (count < threshold).
5. **Given** the Administrator generates a new batch of 20 booklets via Phase 1 (returning `In Stock` count from 2 to 22, well above threshold), **When** a later Sales Invoice that same day drops the count again below threshold, **Then** whether the day's dedup has already fired determines behaviour — if it fired earlier, no new notification today; if it has not fired today yet, one fires. Dedup is per calendar day, not per threshold-crossing.
6. **Given** a Sales Invoice is submitted that does not reference any `Purisol Coupon Booklet` line (non-booklet invoice), **When** the invoice submit completes, **Then** the warehouse check runs but the `In Stock` count is unchanged from before — if it was already below threshold and today has already fired, no notification; if it has not fired today yet and count is below threshold, one fires. Any Sales Invoice submit is a valid evaluation trigger even when no booklets change hands.

### User Story 4 - Notify Administrator When a Booklet Is Fully Consumed (Priority: P2)

When Phase 4's Coupon Consumption Entry on-submit logic transitions a booklet from `Sold` to `Depleted` (because the 20th and last `Available` coupon in the booklet just flipped to `Consumed`), the system sends a bell-icon notification to every administrator user announcing that the booklet is fully consumed and that the customer is a candidate for a resale follow-up. The message names the booklet (`WP-xxxxx`) and the customer who owned it. The click-through routes to the booklet record, where the Administrator can see the full depletion history and decide whether to contact the customer. Because this notification is emitted from inside the consumption-entry transition code (not as a doc-level state-change observer), it fires exactly once per booklet lifecycle — the moment `status` flips to `Depleted` and `depleted_on` is stamped.

**Why this priority**: The depletion notification is the shop's cue to call the customer back for a new purchase — the revenue flywheel for a water-coupon business. Same P2 tier as Story 3 because the revenue implication is slower-moving (customers do not urgently need the notification the same day; a one-to-two-day follow-up window is fine) and because the same information is visible on the Phase 8 dashboard's "Recent Depleted Booklets" widget. But it is still worth shipping — the bell alert is more timely than waiting for someone to log in and look at the dashboard.

**Independent Test**: Can be fully tested by (a) seeding one customer, one administrator user, one booklet `WP-00001` `Sold` to the customer with 19 coupons already consumed and coupon `CP-00020` still `Available`; (b) submitting a Consumption Entry for `CP-00020`. Verify Phase 4's existing logic transitions the booklet to `Depleted` and stamps `depleted_on`, and verify exactly one Booklet Depleted Notification Log entry is created per administrator user, with `document_type = "Purisol Coupon Booklet"`, `document_name = "WP-00001"`, and body naming the customer and the booklet.

**Acceptance Scenarios**:

1. **Given** booklet `WP-00001` is `Sold` with 19 coupons consumed and one coupon `CP-00020` `Available`, **When** a Coupon Consumption Entry consumes `CP-00020`, **Then** exactly one Booklet Depleted Notification Log entry is created per administrator user, with the booklet name and customer name in the body and `document_type`/`document_name` pointing at the booklet record.
2. **Given** a single Consumption Entry deplete **two** booklets at once (e.g. consumes the last remaining coupon of `WP-00001` and the last remaining coupon of `WP-00002` in the same submit), **When** the entry is submitted, **Then** two separate Booklet Depleted notifications are created per administrator user — one per booklet.
3. **Given** a Consumption Entry consumes the 19th coupon of a booklet (not the 20th — booklet is still `Sold`, not yet `Depleted`), **When** the entry is submitted, **Then** no Booklet Depleted notification fires.
4. **Given** a booklet transitioned to `Depleted` a week ago, **When** any unrelated event occurs (e.g. another booklet is sold, an unrelated consumption entry is submitted), **Then** no duplicate Booklet Depleted notification fires for the already-depleted booklet — the notification is emitted only at the one moment of transition.
5. **Given** a future phase or manual script were to re-flip a booklet's status from `Depleted` back to `Sold` and then deplete it again (hypothetically — the Phase 1 constitution forbids this, but testing the guard), **When** that second depletion occurs, **Then** the notification fires again at the moment of the (second) transition — the trigger is state-transition, not "first-time-only" — but this path is explicitly outside MVP expectations.

### Edge Cases

- **Notification transaction semantics**: Notification Log entries are created within the same database transaction as the triggering event (Consumption Entry submit, Discrepancy insert, Sales Invoice submit). If the triggering submit itself rolls back (Phase 4 blocking validation fails, Phase 3 validation fails, etc.), no Notification Log entries persist — the notification and the state change are atomic together. No orphaned notifications for events that never actually happened.
- **No Administrator users exist**: Every trigger evaluates the user set, gets an empty list, and silently no-ops. No error is raised, no partial state is left. This must not block the underlying business event (discrepancy creation, invoice submit, etc.).
- **Disabled user with the Administrator role**: If a user holds the `Purisol Administrator` role but their `User.enabled = 0`, they are excluded from the recipient set. Notifications only go to currently-enabled users.
- **Threshold = 0**: Valid configuration. `customer_low_stock_threshold = 0` means only fire when a customer has literally zero remaining; `warehouse_low_stock_threshold = 0` means never fire (since the `In Stock` count is never strictly less than 0). Phase 6 does not validate thresholds — it honours whatever integer the Administrator sets.
- **Threshold changed mid-transaction**: If the Administrator changes a threshold while a long-running Consumption Entry submit is in flight (extremely rare given MVP volumes, but theoretically possible under contention), the trigger evaluation uses whichever value is read by the evaluation query — there is no explicit snapshot. This is acceptable because Phase 6 reads thresholds fresh at each trigger evaluation and the "live-edit" guarantee is intentionally "at most one submit of stale evaluation before new value takes effect".
- **Warehouse dedup key timing**: The "once per calendar day" dedup uses the server's local date — the same calendar date the Frappe platform uses natively for date-only comparisons. If a shop spans a day boundary at exactly the moment a Sales Invoice submits — the invoice posting time is on the old day but the trigger runs after midnight — the dedup key follows the server clock at trigger time, not the invoice's posting datetime. In practice the difference is sub-second.
- **A booklet whose depletion happens via a future path (not Consumption Entry)**: Phase 6 hooks into Phase 4's depletion code path specifically, as the plan requires. If any future feature sets a booklet's status to `Depleted` through a different path without calling the notify utility, no notification fires. That is acceptable because the Phase-1 constitution already forbids transitioning a booklet to `Depleted` through any route other than Consumption Entry.
- **Customer low-stock re-evaluation when a customer was already below threshold before the submit**: If a customer has total remaining = 2 before a Consumption Entry and = 1 after, the notification fires. The trigger is "total remaining ≤ threshold after the submit", not "threshold just crossed". The Administrator may receive multiple customer-low-stock notifications for the same customer across several consumption entries in a day — this is intentional for MVP (maximum visibility; dedup can be added later if noise becomes a problem).
- **A discrepancy is inserted by a manual admin action, not through Consumption Entry submit**: The New Discrepancy Opened notification is hooked into the `Purisol Coupon Discrepancy` `after_insert` event, which fires regardless of which code path inserted the record. In Phase 5, only the Consumption Entry on-submit logic inserts discrepancies; Phase 6 does not assume that — if a future path inserts one manually, the notification still fires.
- **Permissions for Notification Log**: Standard ERPNext semantics — each user sees only their own Notification Log entries in the bell icon. Phase 6 does not introduce any custom permission logic on Notification Log.
- **Pluggable channel abstraction**: The `Purisol Notify.send()` function does not accept a `channel` argument in Phase 6 — the channel is internal to the utility. A later phase that adds email / SMS / WhatsApp will either consult `Purisol Settings` (new fields per channel) or iterate through a channel registry. Phase 6 ships the single-channel bell-only implementation. Trigger call sites will not need to change.
- **Localization**: All four notification subjects and bodies are fully localizable so they render correctly in both English and Arabic (per the constitution's localization principle). Field interpolation — booklet name, customer name, counts — happens after translation of the shell phrase, so translations need only cover the fixed phrases, not the dynamic data.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: System MUST provide a single `Purisol Notify` utility — a plain Python module, not a DocType, not a DocType controller — with one public function `send(recipient, subject, message, reference_doctype, reference_name)` that every Phase 6 trigger calls. Trigger sites MUST NOT create `Notification Log` records directly; they MUST route through this utility.
- **FR-002**: `Purisol Notify.send()` MUST accept `recipient` as either a `User` name (string) or a `Role` name (string). When `recipient` is a role, the utility MUST expand it into the set of enabled users currently holding that role and emit one notification per user.
- **FR-003**: In Phase 6, `Purisol Notify.send()` MUST deliver notifications exclusively via ERPNext `Notification Log` records (the bell-icon channel). The utility MUST be structured so a future phase can add email / SMS / WhatsApp channels by editing only the utility's internals — trigger-site call sites do not change.
- **FR-004**: On every `Purisol Coupon Discrepancy` insert, system MUST send a New Discrepancy Opened notification to every user holding the `Purisol Administrator` role. The notification's `reference_doctype` MUST be `"Purisol Coupon Discrepancy"` and `reference_name` MUST be the inserted discrepancy's name. The subject and body MUST include the discrepancy's name, type, booklet, and the delivery man on the triggering consumption entry, with every fixed phrase localizable into both English and Arabic.
- **FR-005**: On every `Purisol Coupon Consumption Entry` submit (after Phase 4 side effects and Phase 5 discrepancy creation have completed), system MUST evaluate, for each unique customer among the affected `Sold` booklets, that customer's total remaining coupon count summed across all their currently-`Sold` (not `Depleted`) booklets. If that total is less than or equal to the current value of `Purisol Settings.customer_low_stock_threshold`, system MUST send one Customer Low Stock notification per administrator user, with `reference_doctype = "Customer"` and `reference_name = <that customer's name>`.
- **FR-006**: Customer Low Stock evaluation MUST read `Purisol Settings.customer_low_stock_threshold` fresh at every Consumption Entry submit — no module-level caching, no restart required after the Administrator edits the value. The same live-read rule MUST apply to `warehouse_low_stock_threshold`.
- **FR-007**: On every Sales Invoice submit (after Phase 3's booklet-status hook has completed), system MUST count `Purisol Coupon Booklet` records with status `In Stock`. If the count is strictly less than `Purisol Settings.warehouse_low_stock_threshold` AND no Warehouse Low Stock notification has already been emitted on the current calendar day, system MUST send one Warehouse Low Stock notification per administrator user with a body mentioning the current `In Stock` count.
- **FR-008**: Warehouse Low Stock notifications MUST be deduplicated at most once per calendar day (server local date). The dedup marker MUST persist beyond a single request — i.e. it MUST survive worker restarts, be visible to concurrent Sales Invoice submits, and reset at the day-boundary rollover. Implementation choice is left open (e.g. query Notification Log for today's existing Warehouse Low Stock entries, or a sentinel field on Purisol Settings) provided the dedup contract holds.
- **FR-009**: Warehouse Low Stock notification's `reference_doctype` MUST be `"Purisol Coupon Booklet"`; `reference_name` MAY be empty (routing to the list view is acceptable when ERPNext supports it, otherwise the click-through behaviour is implementation-defined).
- **FR-010**: In Phase 4's booklet-depletion code path (the point where a booklet transitions from `Sold` to `Depleted` and `depleted_on` is stamped), system MUST call `Purisol Notify.send()` once per depleted booklet, sending a Booklet Depleted notification to every administrator user. The notification's `reference_doctype` MUST be `"Purisol Coupon Booklet"` and `reference_name` MUST be the newly-depleted booklet's name; the body MUST include the booklet name and the customer name.
- **FR-011**: If a single Consumption Entry depletes two or more booklets (all their remaining coupons consumed in one submit), system MUST emit one Booklet Depleted notification per depleted booklet — i.e. per administrator user, N notifications for N depleted booklets.
- **FR-012**: Every notification's subject and body MUST be fully localizable — fixed phrases translated per the user's locale, dynamic fields (names, counts, types) interpolated into the translated shell phrase. Both English and Arabic MUST render correctly (per the constitution's localization principle).
- **FR-013**: The `Purisol Administrator` role MUST be the recipient role for all four triggers. System MUST NOT hard-code individual User names anywhere in Phase 6 — every trigger site passes the role, and the utility expands it.
- **FR-014**: When a role expansion returns an empty set of enabled users (i.e. no user currently holds the `Purisol Administrator` role), `Purisol Notify.send()` MUST silently no-op — no error, no partial writes, no exceptions propagated to the caller. The triggering business event (discrepancy insert, invoice submit, etc.) MUST still succeed.
- **FR-015**: Notification creation MUST happen within the same database transaction as the triggering event. If the triggering event rolls back (validation error in the same submit), no Notification Log entries MUST persist for that event.
- **FR-016**: System MUST NOT introduce any new fields, DocTypes, or child tables in Phase 6. Thresholds (`customer_low_stock_threshold`, `warehouse_low_stock_threshold`) already exist on `Purisol Settings` from Phase 1 and are simply consumed. The warehouse-dedup state MAY be stored on `Purisol Settings` as a new transient field if that implementation is chosen, but the decision is left open.
- **FR-017**: Resolution of a discrepancy (Phase 5's `Resolved - *` submit) MUST NOT trigger any Phase 6 notification. Phase 6 notifies on discrepancy **insert**, not on subsequent state changes.
- **FR-018**: Cancellation or amendment of a Consumption Entry, Sales Invoice, or Discrepancy MUST NOT emit any Phase 6 notification. Phase 6 triggers fire only on the initial submit / insert event, not on cancel / amend; cleanup of already-delivered notifications is out of scope for MVP.
- **FR-019**: System MUST retain `Notification Log` entries indefinitely (standard ERPNext behaviour — no custom cleanup / retention logic in Phase 6). Administrators can clear their own bell notifications through standard ERPNext UI.

### Key Entities *(include if feature involves data)*

- **Purisol Notify utility (Python module, no DocType)**: A single module exposing one public `send(recipient, subject, message, reference_doctype, reference_name)` function. Internally, it resolves `recipient` to a list of enabled users (role-expanding if needed) and, for each user, creates an ERPNext `Notification Log` entry. In Phase 6 the only channel is bell-icon Notification Log; the module's signature is intentionally channel-agnostic so later phases add email / SMS / WhatsApp internally.
- **ERPNext Notification Log (reused, not new)**: Standard ERPNext DocType that powers the bell icon. Phase 6 creates entries on it with `for_user`, `subject`, `email_content` (body), `document_type`, `document_name`, and the default `type = "Alert"`. Read-only from Phase 6's perspective after creation; Administrators clear entries through standard ERPNext UI.
- **Purisol Administrator role (reused, defined by the Phase-0 constitution)**: The role whose user set receives every Phase 6 notification. Phase 6 does not define the role — it reads from it.
- **Purisol Settings thresholds (reused, not new)**: Two Int fields on the `Purisol Settings` singleton — `customer_low_stock_threshold` (default 3) and `warehouse_low_stock_threshold` (default 5) — already exist from Phase 1. Phase 6 is the first phase to read them; administrators can edit them live through the Settings form.
- **Warehouse low-stock dedup marker (implementation-defined)**: Some persistent, per-calendar-day state that prevents the Warehouse Low Stock trigger from firing more than once per day. This MAY be a new Date field on `Purisol Settings`, or a query over Notification Log for today's existing warehouse-low-stock entries, or an equivalent mechanism. The contract is "fires at most once per calendar day"; the storage choice is left to the plan.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: For every `Purisol Coupon Discrepancy` record inserted by Phase 5's detection logic, a `Notification Log` entry exists for every currently-enabled user with the `Purisol Administrator` role — 100% of the time, with correct subject, body, and click-through reference.
- **SC-002**: For every unique customer among the booklets affected by a Coupon Consumption Entry submit whose total remaining coupons (summed across their currently-`Sold` non-`Depleted` booklets after the submit's side effects) is less than or equal to `customer_low_stock_threshold`, a Customer Low Stock notification is created per administrator user — exactly once per (entry, customer) pair, with 100% accuracy.
- **SC-003**: When a Sales Invoice submit drops the `In Stock` booklet count strictly below `warehouse_low_stock_threshold`, a Warehouse Low Stock notification is created per administrator user **on the first qualifying submit of the day**; subsequent qualifying submits on the same calendar day create zero additional Warehouse Low Stock notifications. The dedup contract holds across at least 50 consecutive same-day submits.
- **SC-004**: When a Consumption Entry causes a booklet to transition from `Sold` to `Depleted`, one Booklet Depleted notification is created per administrator user per depleted booklet — 100% of the time, with the correct booklet name and customer name in the body.
- **SC-005**: Editing a threshold value on `Purisol Settings` takes effect on the **next** triggering event (Consumption Entry submit or Sales Invoice submit), with no restart or cache invalidation step. Verified by editing a threshold and triggering the relevant event within the same session.

## Assumptions

- **Notification channel**: Phase 6 delivers via ERPNext's built-in `Notification Log` (the bell-icon dropdown) exclusively. Email, WhatsApp, SMS, and every other channel are explicitly deferred. The `Purisol Notify` utility's signature is channel-agnostic precisely so a later phase can add channels internally.
- **Recipient resolution**: Recipient is always the `Purisol Administrator` role. The utility expands the role to the set of enabled users holding it and sends one Notification Log entry per user. This is the ERPNext-idiomatic way to make a role-scoped alert actually reach each person's bell icon (which is per-user).
- **Customer Low Stock re-fire policy**: The trigger fires on every Consumption Entry submit for which a customer's post-submit total remaining is at or below threshold — even if the customer was already below threshold before the submit. MVP favours maximum visibility over dedup. Per-customer daily dedup is a potential Phase-6.1 enhancement but is not part of MVP; noise reduction is deferred to user feedback.
- **Warehouse Low Stock dedup key**: The dedup scope is one calendar day in the server's local time zone (the same "today" that Frappe uses natively for date-only comparisons). The first qualifying Sales Invoice submit of the day sends one notification per administrator user; subsequent same-day qualifying submits send zero. At midnight the counter resets. Implementation storage (new Date field on `Purisol Settings` vs. query-based check against `Notification Log`) is left to the plan phase.
- **Warehouse dedup does NOT gate other triggers**: The per-calendar-day dedup is specific to the Warehouse Low Stock trigger. Customer Low Stock, New Discrepancy Opened, and Booklet Depleted have no dedup — they fire on every qualifying event.
- **Trigger placement**: Each trigger is wired at a specific, explicit call site:
    - New Discrepancy Opened — `Purisol Coupon Discrepancy` DocType controller's `after_insert` method.
    - Customer Low Stock — called from inside Phase 4's Coupon Consumption Entry `on_submit` controller, after Phase 5's discrepancy creation has completed. Running in the same transaction guarantees atomicity.
    - Warehouse Low Stock — called from a `doc_events` hook on ERPNext `Sales Invoice` `on_submit`, after Phase 3's booklet-status hook has run. Phase 6 registers its hook alongside Phase 3's.
    - Booklet Depleted — called from inside Phase 4's booklet-depletion code path, at the same site that flips `status` to `Depleted` and sets `depleted_on`.
- **Atomicity**: Every trigger runs within the same database transaction as its triggering business event. If the business event fails and rolls back, the Notification Log inserts roll back with it. Phase 6 does NOT defer notification delivery to a background job — notifications are synchronous with the trigger so the atomicity contract holds. Sync delivery is acceptable for MVP volumes (< 200 notifications/day).
- **Phase-6 does not modify Phase-1/2/3/4/5 DocType JSON**: The only code changes are (a) a new `Purisol Notify` utility module inside the app, (b) new calls to that utility from existing controllers, (c) a new doc-event registration on Sales Invoice `on_submit`, (d) optionally a new transient field on `Purisol Settings` for warehouse dedup. No Phase 1–5 schema is altered except that last optional transient-field addition.
- **Dedup storage, if using Purisol Settings**: If the plan opts to store the warehouse dedup marker on `Purisol Settings` (e.g. a `last_warehouse_low_stock_notified_on` Date field), that is the only new schema introduced by Phase 6 and it is a simple Date field that does not affect any other phase's logic. The alternative (query-based dedup) requires no schema change at all.
- **No new notifications for `Unassigned Booklet` discrepancies beyond the generic New Discrepancy Opened**: The PRD lists a single "New Discrepancy Opened" trigger that covers both Missing Coupons and Unassigned Booklet discrepancy types. Phase 6 does not differentiate — one notification per discrepancy, whatever its type. The type is named in the subject / body.
- **Localization**: Arabic and English are both supported through the standard Frappe translation workflow — every fixed phrase in every notification is marked for translation, and the app's translation files are updated with the new Arabic strings as part of Phase 6 delivery. No right-to-left-specific layout work is needed on the bell icon (ERPNext core handles it).
- **Dependency: Phase-0 constitution defines the Purisol Administrator role**: Phase 6 assumes the role already exists (created by the constitution or by a setup fixture). If the role is missing in a given environment, role expansion returns empty and all triggers silently no-op — this degrades the feature gracefully but should be caught by environment setup, not by Phase 6 validation.
- **Dependency: Phases 1–5 shipped and stable**: Phase 6 reads post-Phase-4 booklet aggregates (for customer low-stock), hooks Phase-5 discrepancy inserts, hooks Phase-3 sales-invoice submits, and extends Phase-4 booklet-depletion code. All prior phases must be in place; Phase 6 does not work in isolation.
- **Dependency: `Notification Log` DocType is available**: Standard ERPNext 15.x ships this DocType. Phase 6 creates records on it through the `Purisol Notify` utility — no custom DocType definition needed.
- **Out of scope: external channels (email / WhatsApp / SMS)**: Explicitly deferred, consistent with the Phase-0 constitution's notification-channel principle.
- **Out of scope: notification-preferences UI**: Administrators cannot opt out of specific notification types in Phase 6 — every administrator user gets every qualifying notification. A preferences panel is deferred.
- **Out of scope: reports and dashboard widgets for notifications**: Phase 7 covers reports; Phase 8 covers the dashboard. Phase 6 ships only the bell-icon alerts themselves.
- **Out of scope: retry / failure handling for Notification Log inserts**: If a Notification Log insert fails for some transient reason, the entire triggering transaction fails and rolls back (standard ERPNext submit-transaction behaviour). Phase 6 does not add its own retry loop.
