# Implementation Plan: Notifications

**Branch**: `006-notifications` | **Date**: 2026-04-19 | **Spec**: [spec.md](./spec.md)
**Input**: Feature specification from `/specs/006-notifications/spec.md`

## Summary

Phase 6 adds four proactive in-system bell-icon alerts on top of the Phase 1–5 stack, routed through a single channel-agnostic `Purisol Notify` server-side utility so later phases can add email/WhatsApp/SMS channels without touching any trigger site. The four triggers — **New Discrepancy Opened** (wired on `Purisol Coupon Discrepancy.after_insert`, fires once per discrepancy per administrator user), **Customer Low Stock** (wired inside `PurisolCouponConsumptionEntry.on_submit` after Phase-5 detection, fires once per unique affected customer whose post-submit total remaining across their currently-`Sold` non-`Depleted` booklets is `<=` the live-read `Purisol Settings.customer_low_stock_threshold`), **Warehouse Low Stock** (wired as a new `Sales Invoice.on_submit` hook in `sales_invoice_hooks.py`, fires once per calendar day when the count of `Purisol Coupon Booklet` with status `In Stock` is `<` `Purisol Settings.warehouse_low_stock_threshold`, deduplicated via a single new Date field on `Purisol Settings`), and **Booklet Depleted** (emitted from the exact Phase-4 code path that flips a booklet `Sold → Depleted` and stamps `depleted_on`, one call per depleted booklet) — each route through `Purisol Notify.send(recipient, subject, message, reference_doctype, reference_name)`. The utility expands a role-shaped `recipient` argument into the set of enabled users holding that role and emits one `Notification Log` entry per user within the caller's submit transaction, so atomicity holds: if the triggering event rolls back, the notification rollback propagates with it. Empty recipient sets are a silent no-op. Every user-visible fixed phrase is wrapped in `frappe._()` / `__()` so Arabic and English both render correctly per constitution IX. Thresholds are read fresh from `Purisol Settings` at every evaluation — no module-level caching, no restart required after the admin edits a threshold.

**Technical approach** (consolidated from research.md):

- **New server-side utility module `cx_purisol/cx_purisol/api/notify.py`** — a plain Python module, not a DocType, not whitelisted. Co-locates with the other Phase 1–5 service modules in `api/` (`discrepancy.py`, `consumption.py`, `booklet_generation.py`, `sell_booklets.py`). Exposes:
  - `send(recipient: str, subject: str, message: str, reference_doctype: str | None = None, reference_name: str | None = None) -> list[str]` — the single public entry point. `recipient` is either an exact `User.name` or an exact `Role.name`; the utility distinguishes via `frappe.db.exists("Role", recipient)` first, falls back to `User` resolution. Returns the list of `Notification Log.name` values it created (possibly empty). All Phase-6 trigger sites call this function and **only** this function.
  - `_resolve_recipients(recipient: str) -> list[str]` — private; returns the list of enabled `User.name`s to target. Role input expands via `Has Role` joined to `User.enabled = 1`; user input returns `[recipient]` iff the user exists and is enabled, else `[]`. Disabled users and non-existent names produce an empty list (FR-014, spec edge case "Disabled user with the Administrator role").
  - `_emit_bell(for_user, subject, message, reference_doctype, reference_name) -> str` — private; creates a single `Notification Log` doc with `type = "Alert"`, `subject`, `email_content = message`, `for_user`, `document_type`, `document_name`; `.insert(ignore_permissions=True)` inside the caller's transaction; returns the created name. Bell is the only channel in Phase 6. A future phase adds `_emit_email`, `_emit_sms`, etc., and `send()` fans out — the trigger sites never change.
  - Zero module-level mutable state — every `send()` call re-resolves recipients and settings fresh, so admin-edited thresholds and user-enabled changes take effect immediately (FR-006).
- **New trigger call from `Purisol Coupon Discrepancy.after_insert`** — add an `after_insert` method on the existing `PurisolCouponDiscrepancy` controller (it already has `before_insert` and `validate`; `after_insert` is additive) that calls `notify.send(recipient="Purisol Administrator", subject=_("Discrepancy {0} opened").format(self.name), message=<localized body>, reference_doctype="Purisol Coupon Discrepancy", reference_name=self.name)`. Body: `_("Discrepancy {0} opened: {1} in booklet {2}, delivery man {3}.")` — the four placeholders are interpolated after translation. The triggering delivery man is looked up via `self.triggering_consumption_entry` → `Purisol Coupon Consumption Entry.delivery_man`. Runs inside the detection service's transaction (the discrepancy `.insert()` is already inside `on_submit` of the consumption entry); a failure here rolls the whole consumption-entry submit back, which is the only atomicity-correct posture per research.md §1.
- **New trigger call inside `PurisolCouponConsumptionEntry.on_submit`** — widen the existing `on_submit` (which already runs Phase-4 side effects and Phase-5 detection via `detect_for_entry`). After `detect_for_entry` returns and the `discrepancies_detected` child rows are persisted, add a final pass that:
  1. **Booklet Depleted**: during the existing per-booklet loop, when `triggered_depletion` flips to `True` and the booklet has been re-saved with `status = "Depleted"`, call `notify.send("Purisol Administrator", subject=_("Booklet {0} depleted").format(booklet.name), message=_("Booklet {0} for customer {1} is fully consumed. Follow up for resale.").format(booklet.name, booklet.customer or _("Unknown")), reference_doctype="Purisol Coupon Booklet", reference_name=booklet.name)`. Emitted from inside the depletion block specifically, not from a generic state-change observer — satisfies FR-010 and spec US4 Acceptance 5.
  2. **Customer Low Stock**: after the per-booklet loop completes, compute the unique set of `booklet.customer` values across all Sold booklets touched by this entry (skip booklets whose customer is null — those are the Unassigned Booklet cases, which never produce a customer-low-stock notification per US2 Acceptance 5). For each such customer, run `total_remaining = frappe.db.sql("SELECT COALESCE(SUM(remaining_count), 0) FROM \`tabPurisol Coupon Booklet\` WHERE customer = %s AND status = 'Sold'", (customer,))[0][0]`. Compare against fresh-read `frappe.get_doc("Purisol Settings").customer_low_stock_threshold` (no cache). If `total_remaining <= threshold`, call `notify.send("Purisol Administrator", subject=_("Customer {0} low on coupons").format(customer_name), message=_("Customer {0} has {1} coupons remaining. Prepare a new booklet.").format(customer_name, total_remaining), reference_doctype="Customer", reference_name=customer)`. `customer_name` resolves via `frappe.db.get_value("Customer", customer, "customer_name") or customer`.
  - Both trigger sites run inside the consumption entry's submit transaction. Any raise from `notify.send()` rolls the whole entry back, which is the correct atomicity posture (notifications are supposed to succeed or fail with the triggering business event per FR-015).
- **New trigger call from `Sales Invoice.on_submit`** — add a function `check_warehouse_low_stock(doc, method=None)` to the existing `cx_purisol/cx_purisol/sales_invoice/sales_invoice_hooks.py`, wired as a second `on_submit` hook via `hooks.py` (`doc_events["Sales Invoice"]["on_submit"]` becomes a list `["cx_purisol.cx_purisol.sales_invoice.sales_invoice_hooks.mark_booklets_sold", "cx_purisol.cx_purisol.sales_invoice.sales_invoice_hooks.check_warehouse_low_stock"]` — Frappe natively supports list-form `doc_events` handlers and runs them in order). `check_warehouse_low_stock`:
  1. Re-reads `settings = frappe.get_doc("Purisol Settings")` fresh.
  2. `in_stock_count = frappe.db.count("Purisol Coupon Booklet", {"status": "In Stock"})`.
  3. If `in_stock_count >= settings.warehouse_low_stock_threshold`, return (no qualifying condition — FR-007 strict inequality).
  4. Compare `settings.last_warehouse_low_stock_notified_on` against `frappe.utils.today()`. If equal, return (already fired today — FR-008 dedup).
  5. Otherwise call `notify.send("Purisol Administrator", subject=_("Warehouse low on booklet stock"), message=_("Only {0} booklets remain in stock. Generate a new batch.").format(in_stock_count), reference_doctype="Purisol Coupon Booklet", reference_name=None)` (empty `reference_name` is valid — Frappe routes to the `Purisol Coupon Booklet` list view). On success, `frappe.db.set_single_value("Purisol Settings", "last_warehouse_low_stock_notified_on", frappe.utils.today())` to persist the dedup marker. Uses `set_single_value` (not a full `save()`) to avoid triggering a recursive validate pass on the settings singleton and to keep the write inside the invoice-submit transaction.
  - Wired as a secondary `on_submit` — the primary (`mark_booklets_sold`) must run first so that the `In Stock` count reflects the post-submit state. Frappe runs `doc_events` handlers in listed order; we list the Phase-6 handler last.
- **One new field on `Purisol Settings`** (the ONLY schema change Phase 6 introduces) — `last_warehouse_low_stock_notified_on`, `fieldtype = "Date"`, read-only, `in_list_view = 0`, hidden under a new section break `section_break_dedup` (or appended to the existing `section_break_warnings`). Default: empty. Used solely by the warehouse-dedup logic. Spec FR-016 explicitly permits this ("MAY be stored on `Purisol Settings` as a new transient field"); research.md §3 rejects the query-based alternative for fragility and concurrency reasons. No other Phase 1–5 DocType JSON changes.
- **One-line widening of `Purisol Coupon Discrepancy` controller** — add an `after_insert(self)` method that calls the utility. No other change to that controller (validate, before_submit, before_insert all stay verbatim).
- **Python changes to `purisol_coupon_consumption_entry.py`** — two additive blocks inside the existing `on_submit`: (i) the notify call in the depletion branch (one line inside the existing `if triggered_depletion:` block), (ii) the customer-low-stock pass after the Phase-5 detection call. No change to validate, before_submit, on_cancel. The import `from cx_purisol.cx_purisol.api import notify` is added alongside the existing `detect_for_entry` import.
- **Python changes to `sales_invoice/sales_invoice_hooks.py`** — add the `check_warehouse_low_stock(doc, method=None)` function. No change to the three existing functions (`validate_booklet_lines`, `mark_booklets_sold`, `reverse_booklets_sale`, `guard_trash`).
- **`hooks.py` changes** — extend `doc_events["Sales Invoice"]["on_submit"]` from a single string to a list of two (current `mark_booklets_sold`, new `check_warehouse_low_stock`). No new `doctype_js` or `doctype_list_js` entries — Phase 6 ships zero client-side JS (bell icon is a core ERPNext feature, no custom UI needed).
- **`patches.txt`** — one new post-model-sync entry `cx_purisol.patches.v0_6_0.add_warehouse_low_stock_dedup_field` — on upgrade, initializes the new `last_warehouse_low_stock_notified_on` field to null (trivial no-op, since the field defaults to empty on fresh install). On fresh install, nothing to do. Matches Phase 2/3/4/5 anchor pattern.
- **Tests**:
  - Unit tests for the utility: `cx_purisol/cx_purisol/api/test_notify.py` — role expansion (role with N enabled users → N Notification Logs; role with zero enabled users → 0 logs, no error; role with disabled users → skipped; non-existent role → 0 logs, no error), user-direct input, reference_name empty (routes to list view), atomicity (intentional raise inside `_emit_bell` rolls back the enclosing transaction).
  - Unit tests for the widened discrepancy controller: extend `doctype/purisol_coupon_discrepancy/test_purisol_coupon_discrepancy.py` with an `after_insert` notification assertion — inserting a discrepancy directly (via `seed_open_discrepancy` from Phase 5 fixtures) creates exactly one Notification Log per administrator user with the expected subject, body, and reference.
  - Widen `doctype/purisol_coupon_consumption_entry/test_purisol_coupon_consumption_entry.py` (if needed) to assert that submitting a no-discrepancy entry creates zero notifications (other than Booklet Depleted when applicable) and that a full-booklet-depleting submit creates one Booklet Depleted notification.
  - Widen `sales_invoice/test_sales_invoice_hooks.py`-equivalent tests (Phase 3 may have co-located under `tests/test_sales_flows.py`) — add tests for the warehouse-low-stock trigger: first qualifying submit fires, second same-day qualifying submit does not, next-day qualifying submit fires again, above-threshold submit does not fire.
  - New integration test file `tests/test_notification_flows.py` — one test per user story: US1 (discrepancy → admin receives alert), US2 (consumption entry drops customer below threshold → alert, and threshold-edit mid-session takes effect), US3 (warehouse-low-stock with dedup across same-day invoices + next-day reset), US4 (20th-coupon consumption → depletion alert).
  - Extend `tests/fixtures.py` with: (a) `seed_administrator_user(email, name=None)` helper that creates a User with `Purisol Administrator` role (idempotent across tests; fresh cleanup); (b) `count_notifications(for_user=None, doctype=None, document_name=None, subject_contains=None)` helper for delta-based assertions; (c) `reset_warehouse_dedup()` helper that clears `Purisol Settings.last_warehouse_low_stock_notified_on` between warehouse-dedup test cases.
- **Translation strings** — every new `_()`-wrapped phrase introduced in this phase appended to `cx_purisol/translations/ar.csv`. The Arabic translations use the numeric placeholder ordering Frappe supports (`{0}`, `{1}`, …) so word order can differ between locales without string surgery.

## Technical Context

**Language/Version**: Python 3.10+ (Frappe server), JavaScript (Frappe client scripts — not used in this phase; zero client-side code is added).
**Primary Dependencies**: Frappe Framework 15.x (`Notification Log`, `Has Role`, `User`), ERPNext 15.x (`Sales Invoice`, `Customer`, `Employee`). No new third-party libraries. Reuses Phase-1 `Purisol Settings` thresholds (`customer_low_stock_threshold`, `warehouse_low_stock_threshold`), Phase-1 `Purisol Coupon Booklet` aggregates (`remaining_count`, `status`, `customer`), Phase-4 `Purisol Coupon Consumption Entry` controller (widened in place), Phase-5 `Purisol Coupon Discrepancy` controller (widened in place with `after_insert`), Phase-3 `sales_invoice_hooks.py` module (adds one new function). Constitution role `Purisol Administrator` already exists as a Phase-0 fixture.
**Storage**: Frappe DocTypes on MariaDB via `frappe.db` / `frappe.get_doc` / `frappe.db.count` / `frappe.db.sql` / `frappe.db.set_single_value`; no raw SQL writes. Zero new custom DocTypes. One field added to `Purisol Settings` (`last_warehouse_low_stock_notified_on`). All Phase-6 writes are inserts on the framework-owned `Notification Log` DocType, plus the one single-value update on `Purisol Settings`.
**Testing**: Frappe test framework (`frappe.tests.utils.FrappeTestCase`), invoked via `bench --site <test-site> run-tests --app cx_purisol`. Tests extend `cx_purisol/cx_purisol/tests/fixtures.py` with Phase-6 helpers for administrator-user seeding, notification-count deltas, and warehouse-dedup reset. Phase 6 uses delta-based assertions (`count_before → count_after`) rather than absolute counts to stay robust against test-run ordering and shared-state (the `Notification Log` table is site-wide and not truncated between tests).
**Target Platform**: Linux server running Frappe Bench (gunicorn + RQ workers + MariaDB + Redis).
**Project Type**: Frappe custom app (`cx_purisol`) — adds one new server-side utility module (`api/notify.py`), widens one existing controller (`PurisolCouponDiscrepancy.after_insert`), widens one existing controller (`PurisolCouponConsumptionEntry.on_submit` — two additive blocks), adds one function to one existing module (`sales_invoice_hooks.py`), adds one `doc_events` wiring to `hooks.py`, adds one Date field to `Purisol Settings`, ships one no-op patch. Zero new DocTypes, zero new roles, zero new client-side JS, zero new custom-field fixtures.
**Performance Goals**:
- Each trigger adds ≤5 small indexed queries to its host submit (role expansion → 1 `Has Role` query + 1 `User` enabled check; Customer Low Stock → 1 `SUM(remaining_count)` per unique customer; Warehouse Low Stock → 1 `COUNT(booklet WHERE status='In Stock')` + 1 single-value read/write on Purisol Settings; New Discrepancy → same role expansion). Notification Log insert is a single row per recipient user. At single-admin single-customer typical operation, Phase 6 adds well under 100 ms per triggering event (SC-010).
- Worst-case daily load: 20 consumption entries × (0–5 customers affected each + 1 possible depletion each) = up to ~200 notifications/day, plus 10–20 discrepancy notifications and 0–1 warehouse notifications. Two orders of magnitude under constitution VIII's 100-records-synchronous threshold. Zero `frappe.enqueue` calls introduced.
**Constraints**:
- **Atomic with triggering event** — Phase 6 notifications create `Notification Log` entries inside the same transaction as the host submit. A raise anywhere rolls the whole thing back; there is no "notification succeeded but business event didn't" or vice versa (FR-015, SC-008).
- **Channel-agnostic `Purisol Notify.send()` signature** — the caller never passes a channel; the utility internally dispatches to bell-only in Phase 6. Adding email / SMS / WhatsApp in a future phase modifies only the utility; the four trigger sites do not change (FR-003, constitution VII).
- **Live-read thresholds** — Phase 6 reads `Purisol Settings` fresh at every trigger evaluation (no module-level caching, no `frappe.get_cached_doc`). Admins can edit a threshold and the next trigger honours it without a restart (FR-006, SC-005).
- **Exactly-once semantics per qualifying event**: New Discrepancy fires once per discrepancy; Booklet Depleted fires once per booklet state transition; Customer Low Stock fires once per (Consumption Entry × unique affected customer) pair; Warehouse Low Stock fires at most once per calendar day. Each trigger's host event is itself a one-shot (each discrepancy is `.insert()`ed once; each booklet transitions to `Depleted` once; each consumption entry is `.submit()`ed once; each Sales Invoice is `.submit()`ed once) so Phase-6 dedup logic is minimal — only the warehouse trigger needs explicit per-day dedup, which is implemented via a single Date field on `Purisol Settings` (FR-008).
- **Silent no-op on empty recipient set** — if the `Purisol Administrator` role has zero enabled users, `notify.send()` completes without creating any Notification Log and without raising. The triggering business event succeeds as if no notification were configured (FR-014, SC-007).
- **Zero mutation of other DocTypes** — Phase 6 does not modify any booklet, coupon, consumption entry, discrepancy, or invoice record beyond inserting the `Notification Log` row and the one single-value write on `Purisol Settings` for warehouse dedup. All Phase 1–5 DocTypes' semantics are preserved.
- **Localization** — every fixed phrase wrapped in `frappe._()` with numeric placeholders (`{0}`, `{1}`, …) that allow Arabic word reordering without string surgery; Arabic translations land in `cx_purisol/translations/ar.csv` as part of the phase (constitution IX, FR-012, SC-006).
- **Permissions** — Phase 6 does not introduce any new role, does not modify any existing role's permission matrix. The `Notification Log` DocType's ERPNext-standard permissions govern bell access (each user reads only their own entries); Phase 6 creates them with `ignore_permissions=True` since the triggering submit already ran the permission check on the host event.

**Scale/Scope**: Single shop. Administrator user set: 1–3. Typical day: 10–50 Sales Invoice submits, 5–20 Consumption Entry submits, 0–5 discrepancies, 0–2 booklet depletions, 0–1 warehouse low-stock events → 10–80 Notification Log rows per admin per day. Multi-tenant / multi-currency / multi-branch variants are out of scope.

All new phrases appended to `cx_purisol/translations/ar.csv` as part of the phase.
