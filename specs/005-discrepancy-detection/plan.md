# Implementation Plan: Discrepancy Detection & Resolution

**Branch**: `005-discrepancy-detection` | **Date**: 2026-04-18 | **Spec**: [spec.md](./spec.md)
**Input**: Feature specification from `/specs/005-discrepancy-detection/spec.md`

## Summary

Phase 5 layers the system's "intelligence" on top of Phase 4's all-or-nothing `Purisol Coupon Consumption Entry` submit. Detection runs **after** Phase 4's blocking validations pass and after the core coupon/booklet side effects have been written, but **inside the same submit transaction**, so either both the consumption and its derived discrepancies commit together or neither does. For each distinct booklet touched by the entry the detector computes the union of (previously-consumed coupons ∪ coupons being consumed now), finds any coupon number strictly between that union's min and max whose current status is `Available` **and** which is not already covered by an `Open` Missing Coupons discrepancy for the same booklet, and — if the resulting set is non-empty — creates one submittable `Purisol Coupon Discrepancy` of type `Missing Coupons`. Independently, for every coupon in the entry whose parent booklet's status is not `Sold`, the detector creates one `Purisol Coupon Discrepancy` of type `Unassigned Booklet` (one per coupon, as spec FR-004 mandates). Every created discrepancy is opened with `status = Open`, `opened_on = now()`, an auto-computed `estimated_amount` derived from the affected booklet's sales invoice line (or the `coupon_item` price-list fallback, or 0), and an auto-populated `related_delivery_men` table listing the booklet's current custody holder (if `In Custody`) plus every delivery man who submitted any Consumption Entry referencing the same booklet in the last 30 days from the triggering entry's `posting_date`. The Consumption Entry's `has_warnings` is flipped to `True`, its reserved-empty `discrepancies_detected` child table (stub from Phase 4) is populated, and the Administrator's client script pops a non-blocking modal listing every new discrepancy.

A separate resolution workflow operates on any `Open` discrepancy. The Administrator sets `resolution_action` to one of `None` (admin error — no financial consequence), `Add to Liability Ledger` (creates a Journal Entry debiting `employee_liability_account` with `party_type = Employee` / `party = liable_delivery_man` and crediting `discrepancy_offset_account`), or `Immediate Cash Payment` (creates a Payment Entry of type `Receive` from `discrepancy_offset_account` to `default_cash_account` referencing the discrepancy). Both financial paths require `liable_delivery_man` and the relevant configured accounts; their errors are blocking and the submit fails atomically if any precondition or downstream write fails. On successful submit, the discrepancy transitions to the appropriate `Resolved - *` state, stamps `resolved_on`, stores the created JE/PE name, and locks under standard ERPNext submittable semantics (amendment disallowed in Phase 5). Discrepancy records are the sole source of truth; all state changes — detection, resolution, linked documents — are fully recoverable from the record itself, satisfying constitution IV.

**Technical approach** (consolidated from research.md):

- **New submittable DocType `Purisol Coupon Discrepancy`** (`is_submittable = 1`, `track_changes = 1`, naming series `PCD-.YYYY.-.#####`). Fields cover discrepancy_type (`Missing Coupons | Unassigned Booklet`), status (5 values: `Open`, `Under Review`, `Resolved - Admin Error`, `Resolved - Delivery Man Liable`, `Resolved - Paid`), timestamps (`opened_on`, `resolved_on`), references (`triggering_consumption_entry`, `booklet`, `customer`), the two child tables (`affected_coupons`, `related_delivery_men`), resolution inputs (`liable_delivery_man`, `estimated_amount`, `resolution_action`, `resolution_notes`), and side-effect outputs (`journal_entry`, `payment_entry`). Permissions: `Purisol Administrator` has full CRUD + submit/cancel; amend = 0 per FR-017.
- **New child table DocType `Purisol Coupon Discrepancy Coupon`** (`istable = 1`) — one row per affected coupon. Fields: `coupon` (Link → Purisol Coupon, reqd, search_index), `coupon_number` (Data, `fetch_from = coupon.coupon_number`, read-only), `notes` (Small Text). For Missing Coupons each row is an `Available` coupon inside the detected gap; for Unassigned Booklet a single row references the submitted coupon.
- **New child table DocType `Purisol Coupon Discrepancy Related Person`** (`istable = 1`) — one row per delivery man touchpoint. Fields: `delivery_man` (Link → Employee, reqd), `role` (Select: `Custody Holder | Submitted Adjacent Coupons`, reqd), `custody_entry` (Link → Purisol Custody Entry, optional), `consumption_entry` (Link → Purisol Coupon Consumption Entry, optional), `notes` (Small Text).
- **Widen the existing Phase-4 stub `Purisol Coupon Discrepancy Item`** so the consumption entry's `discrepancies_detected` child table now carries a real link. The stub already has a `notes` field and a live schema; Phase 5 adds one `discrepancy` link field pointing at `Purisol Coupon Discrepancy` (plus read-only fetched `discrepancy_type` for list display). This is strictly additive — Phase 4's validate (reject non-empty) is **relaxed** in Phase 5 but the Phase 4 controller code is widened, not rewritten (see below).
- **Widen the existing `Purisol Coupon Consumption Entry` controller** — no JSON change; only the Python controller gains a post-Phase-4 detection pass and relaxes the two reserved-empty guards (`has_warnings`, `discrepancies_detected`) which were Phase-4 defensive throws. Specifically:
  - `validate` drops the two defensive throws introduced in Phase 4 (V4, V5 from Phase 4's data-model). The fields may now be populated — but **only** by the controller during submit, never by a human form edit. Form field remains `read_only = 1`; server-side controller writes via `db_set`/`append`.
  - `on_submit` adds a final pass — after the existing coupon/booklet mutations — that invokes `cx_purisol.cx_purisol.api.discrepancy.detect_for_entry(self)`. The helper runs both detection rules, creates and submits each resulting `Purisol Coupon Discrepancy` (one `.save()` + `.submit()` per), appends a row to the entry's `discrepancies_detected` table for each, and sets `self.has_warnings = 1` if any were created. Because this runs inside the same `on_submit` transaction, a failure in any discrepancy creation rolls the whole Consumption Entry submit back — which is the only way to honor FR-001 + FR-002 together ("detection happens in the submit transaction" and "detection MUST NOT block the entry"). The apparent tension is resolved in research.md §1: detection logic itself never raises business-rule errors — it only raises on infrastructure failures (DB error, serialization failure). A purely-read detection pass that then writes only fresh `Discrepancy` docs cannot logically fail the entry's data; if a low-level write truly fails, rolling back the whole thing is the correct posture (the entry was ambiguously-persisted at that point anyway).
  - The `on_cancel` path is **not** widened to auto-cancel linked discrepancies (spec edge case "Cancellation of a consumption entry that created discrepancies — Out of scope for MVP"). Those are left as-is for the Administrator to handle manually through the resolution flow.
- **New discrepancy-detection service module `cx_purisol/cx_purisol/api/discrepancy.py`** (not a whitelisted endpoint — pure server-side service called from the consumption entry controller):
  - `detect_for_entry(entry: PurisolCouponConsumptionEntry) -> list[str]` — returns the names of every discrepancy created. Internally calls `_detect_missing_coupons(entry)` and `_detect_unassigned_booklets(entry)`.
  - `_detect_missing_coupons(entry)` — for each distinct `booklet` in `entry.coupons`: union the booklet's `Consumed` coupons (post-Phase-4 update, so `entry`'s own coupons are now `Consumed`), compute `min..max` from the `page_number` values of that set, identify gap pages whose coupon row is still `Available`, subtract every coupon already listed in `affected_coupons` of any `Open` Missing Coupons discrepancy for the same booklet (idempotence — FR-010), and — if non-empty — build and `.submit()` one discrepancy per booklet.
  - `_detect_unassigned_booklets(entry)` — for each row in `entry.coupons` whose `booklet.status != "Sold"`, build and `.submit()` one discrepancy (one per coupon — FR-004).
  - `_auto_populate_related_delivery_men(discrepancy, entry, booklet)` — given the discrepancy-in-construction, appends (a) one `Custody Holder` row iff `booklet.status == "In Custody"` using the booklet's most-recent `Purisol Custody Entry Assign` row as the `custody_entry` reference, and (b) one `Submitted Adjacent Coupons` row per distinct delivery man who submitted any `Purisol Coupon Consumption Entry` referencing `booklet` within 30 days of `entry.posting_date` (exclusive of `entry` itself), referencing the most-recent such entry per delivery man. Note: the 30-day window anchors to `entry.posting_date`, not to `now()` (spec Assumption).
  - `_compute_estimated_amount(booklet, affected_coupons_count) -> float` — returns `coupon_unit_price × count`. Price resolution order matches the spec Assumption: (1) booklet's `sales_invoice` → Sales Invoice Item line whose `purisol_booklet` custom field points at this booklet → `rate / 20`; (2) `frappe.get_doc("Purisol Settings").default_price_list` → Item Price for `Purisol Settings.coupon_item` in that price list → `price_list_rate / 20`; (3) `0.0` fallback.
  - `_list_open_missing_coupon_names(booklet) -> set[str]` — flattens `affected_coupons.coupon` across every `Open` Missing Coupons discrepancy for the booklet. Used by `_detect_missing_coupons` for dedup. Resolved discrepancies are intentionally **not** included in the exclusion set (spec Assumption: "Resolved discrepancies do not provide this protection").
- **Discrepancy controller (`purisol_coupon_discrepancy.py`)** — holds resolution logic; detection-time population happens in the service above and is already persisted by the time the first `validate` runs.
  - `before_insert` — if `status` is empty, set to `Open`; if `opened_on` is empty, set to `now()`. Defensive — the service populates these explicitly.
  - `validate` — while `docstatus == 0` (draft/Open), re-compute `estimated_amount` only if the administrator has not manually edited it (sentinel via `get_doc_before_save()`). Allow editing of `resolution_action`, `liable_delivery_man`, `resolution_notes`, `estimated_amount`; reject edits to detection-time fields (`discrepancy_type`, `triggering_consumption_entry`, `booklet`, `customer`, `affected_coupons`, `related_delivery_men`) via field-by-field comparison against `get_doc_before_save()`. Enforce status transitions: `Open → Under Review` (via save) allowed; any transition into a `Resolved - *` state is only allowed via submit (below). Locked state (`docstatus == 1`) is enforced by Frappe's built-in "cannot edit submitted document" — no custom code; FR-017 satisfied.
  - `before_submit` — branch on `resolution_action`:
    - `None`: require nothing beyond what's already set. Set `status = "Resolved - Admin Error"`, `resolved_on = now()`.
    - `Add to Liability Ledger`: require `liable_delivery_man`; require `Purisol Settings.employee_liability_account` and `.discrepancy_offset_account`; throw a single aggregated error if any missing. Create the Journal Entry (code below) and store its name in `self.journal_entry`; set `status = "Resolved - Delivery Man Liable"`, `resolved_on = now()`.
    - `Immediate Cash Payment`: require `liable_delivery_man`; require `Purisol Settings.discrepancy_offset_account` and `.default_cash_account`; throw aggregated error if any missing. Create the Payment Entry and store its name in `self.payment_entry`; set `status = "Resolved - Paid"`, `resolved_on = now()`.
  - `on_submit` — no further work; all side effects were performed in `before_submit` so they participate in the same transaction and a downstream Frappe framework error rolls everything back (FR-013 last sentence, FR-015).
  - Helpers `_create_liability_journal_entry(doc)` and `_create_cash_payment_entry(doc)` isolate the ERPNext primitives. Both `.insert()` + `.submit()` the created document in the same transaction.
- **Client script (`public/js/purisol_coupon_consumption_entry.js` — widen existing)** — after a successful submit that returns `docinfo` with `has_warnings = 1` and non-empty `discrepancies_detected`, the script shows a non-blocking modal dialog (Frappe's `frappe.msgprint` with `indicator = "orange"`, `wide = True`) listing each discrepancy by name, type, booklet, and affected coupon count, each rendered as a click-through link. Script only runs for `Purisol Administrator` (the only role that can submit the entry). Localized via `__()`.
- **Client script (`public/js/purisol_coupon_discrepancy.js` — new)** — two concerns:
  1. When `resolution_action` is edited on an `Open` draft, toggle visibility / reqd on `liable_delivery_man` (hidden & optional for `None`; visible & reqd for both financial paths).
  2. Render a read-only "Related Delivery Men" shortlist banner on form load so the administrator can pick the liable one with one click.
- **List view via `public/js/purisol_coupon_discrepancy_list.js` (new)** — sets the default list filter to `status = Open` when the list loads without an explicit filter, sort by `opened_on desc`. Columns are default JSON columns (discrepancy_type, booklet, customer, estimated_amount, opened_on).
- **`hooks.py` updates** — one new `doctype_js` entry for `Purisol Coupon Discrepancy`, one new `doctype_list_js` entry for the list view filter. No new `doc_events` (all detection is controller-owned; all resolution is controller-owned). Fixture list unchanged (no new role, no new custom field).
- **`patches.txt`** — one new post-model-sync entry `cx_purisol.patches.v0_5_0.relax_consumption_entry_reserved_guards` — a no-op anchor on fresh installs, matches Phase 2/3/4 pattern; documents "this site has been migrated through Phase 5" and serves as a hook for future clean-up work if needed.
- **Idempotence**: `_detect_missing_coupons` is idempotent across submits — a second submit that re-detects the same gap produces zero records (FR-010, SC-004). Unassigned Booklet is per-coupon so it is naturally idempotent by construction (a coupon submitted twice would fail Phase 4's "already consumed" blocker first).
- **Concurrency**: detection reads `Purisol Coupon` and `Purisol Coupon Booklet` state post-Phase-4 update, all inside the submit transaction. Two concurrent Consumption Entry submits touching the same booklet serialize on the booklet row (Phase-4 `booklet.save(ignore_permissions=True)`); whichever commits second sees the first's coupon flips and computes a correct gap against the merged state. The discrepancy dedup read is done inside the same transaction so no race window exists between "check for open discrepancy" and "create new discrepancy". No pessimistic locking is added; optimistic locks (`modified` stamp) suffice because all writes are fresh rows (no update-vs-update conflict on discrepancy records).
- **Tests**:
  - Unit tests: `test_purisol_coupon_discrepancy.py` (validate rules, status-transition rules, submit-time account checks, amend disabled), `test_purisol_coupon_discrepancy_coupon.py` (trivial — link integrity), `test_purisol_coupon_discrepancy_related_person.py` (role options; link integrity).
  - Service tests: `api/test_discrepancy.py` — each helper in isolation: gap computation with every edge case from spec (no gap at top, no gap at bottom, interior gap, dedup against open, partial-overlap dedup); unassigned detection; estimated-amount resolution order; related-delivery-men auto-population.
  - Integration tests: `tests/test_discrepancy_flows.py` — one test per user story (Missing Coupons, Unassigned Booklet, Admin Error resolution, Liability resolution with JE creation, Cash Payment resolution with PE creation, list + modal surfaces) plus one test per edge case (gap below min, gap above max, re-detect dedup, mixed anomalies in one entry, depleted-booklet-with-open-discrepancy, settings change between detection and resolution).
  - Test fixtures extend `tests/fixtures.py` with helpers to: (a) stand up a booklet in each relevant state, (b) pre-configure the three Purisol Settings accounts with valid GL accounts, (c) create open discrepancies directly for resolution-path tests.

## Technical Context

**Language/Version**: Python 3.10+ (Frappe server), JavaScript (Frappe client scripts).
**Primary Dependencies**: Frappe Framework 15.x, ERPNext 15.x (`Employee`, `Customer`, `Sales Invoice`, `Sales Invoice Item`, `Journal Entry`, `Payment Entry`, `Account`, `Price List`, `Item Price`). No new third-party libraries. Reuses Phase-1 reserved account fields on `Purisol Settings` (`employee_liability_account`, `discrepancy_offset_account`, `default_cash_account`), Phase-2 `Purisol Custody Entry` for custody-holder lookup, Phase-3 `Sales Invoice Item.purisol_booklet` custom field for price-line lookup, Phase-4 `Purisol Coupon Consumption Entry` + `Purisol Coupon Discrepancy Item` stub.
**Storage**: Frappe DocTypes on MariaDB via `frappe.db` / `frappe.get_doc` / `frappe.get_all`; no raw SQL writes. Three new custom DocTypes (one submittable parent + two child tables) and one minor JSON widening of the Phase-4 discrepancy stub (one new Link field). No schema change to any Phase 1/2/3/4 DocType beyond the `Purisol Coupon Discrepancy Item` widening.
**Testing**: Frappe test framework (`frappe.tests.utils.FrappeTestCase`), invoked via `bench --site <test-site> run-tests --app cx_purisol`. Tests extend `cx_purisol/cx_purisol/tests/fixtures.py` with Phase-5 setup: pre-configured accounts, a helper that drives a booklet to a specific consumed-set state, a helper that creates an Open discrepancy directly (bypassing the detection path for resolution-only tests).
**Target Platform**: Linux server running Frappe Bench (gunicorn + RQ workers + MariaDB + Redis).
**Project Type**: Frappe custom app (`cx_purisol`) — adds three DocTypes (one submittable parent, two child tables), widens one existing child-table stub JSON (`Purisol Coupon Discrepancy Item` — add one link field), widens the existing `Purisol Coupon Consumption Entry` controller (no JSON change), adds one server-side service module (`api/discrepancy.py` — not whitelisted), and adds three client scripts (entry modal widening + new discrepancy form + new discrepancy list).
**Performance Goals**:
- A typical Consumption Entry submit that creates zero discrepancies completes in the same wall-clock envelope as Phase 4 — detection is an additional ~10–20 ms pass over the entry's coupons + one `frappe.get_all` per booklet + one `frappe.get_all` over the last 30 days of consumption entries for each booklet (all indexed lookups, trivial at single-shop scale). SC-012 validates this.
- A worst-case Consumption Entry touching 20 booklets that all simultaneously detect Missing Coupons creates 20 new discrepancy documents — each document's insert + submit is ~4 writes (parent + two child rows average + tabVersion); 80 row writes, well under the gunicorn 120 s synchronous threshold.
- Resolution submit creates one JE or PE; at Purisol scale this is a single-digit ms of additional work on top of the resolution save itself.
**Constraints**:
- Atomic all-or-nothing Consumption Entry submit — Phase 5 cannot partially succeed (some discrepancies created, others not). If detection raises, the whole Consumption Entry rolls back (FR-001 + FR-002 resolved via "detection never has business-rule errors"; see research.md §1).
- Discrepancy submit is atomic: either the JE/PE creates successfully and the discrepancy transitions to Resolved-*, or the whole submit rolls back and the discrepancy stays Open (FR-013, FR-015).
- Discrepancy detection MUST NOT mutate any coupon, booklet, or consumption entry record (FR-021). The detection service only reads and creates fresh `Purisol Coupon Discrepancy` + child rows.
- Amendment on `Purisol Coupon Discrepancy` is explicitly disabled (`amend = 0` in permissions) — corrections go through reversing JEs/PEs (FR-017, constitution IV "audit trail by default").
- Every user-facing string (error messages, modal text, status labels, role options, select-field options) wrapped in `frappe._()` / `__()` (constitution IX); Arabic translations land in the existing `cx_purisol/translations/ar.csv`.
- Only `Purisol Administrator` can read/write/submit/cancel `Purisol Coupon Discrepancy` (constitution VI). System Manager has read-only access for audit purposes (parallels Phase-4's pattern).
- Zero notification code in Phase 5 (FR-009's "modal dialog" is a client-script concern, not a Notification DocType). Bell-icon and other channels remain a Phase-6 seam.
- Zero report code beyond the basic default list view with a saved `status = Open` filter (Phase-7 owns the delivery-man discrepancy-rate reports).

**Scale/Scope**: Single shop. Open discrepancies at steady state: handfuls (order of magnitude 1–10). Lifetime discrepancies: low hundreds. Per-Consumption-Entry detected discrepancy count: 0–3 typical, up to ~20 in the worst-case full-route entry (one Missing Coupons per booklet). Multi-branch / multi-currency / bulk-day discrepancy handling is out of scope.

## Constitution Check

Constitution version: **1.0.0** (10 principles). The plan-template's Constitution Check section is still a placeholder (known TODO in the Sync Impact Report). The 10 principles below are evaluated explicitly for this phase.

| # | Principle | Status | Evidence |
|---|-----------|--------|----------|
| I | Naming Convention | **PASS** | Three new DocTypes — `Purisol Coupon Discrepancy`, `Purisol Coupon Discrepancy Coupon`, `Purisol Coupon Discrepancy Related Person`. All four words capital-first, single trailing space after "Purisol". The pre-existing stub `Purisol Coupon Discrepancy Item` (from Phase 4) is untouched in name and retains the convention. No non-prefixed Purisol DocType is created. |
| II | Leverage ERPNext Primitives | **PASS** | Financial consequences of a resolved discrepancy flow through ERPNext's native `Journal Entry` (for liability) and `Payment Entry` (for cash) — no custom ledger or cash-book is created. `liable_delivery_man` is a Link to `Employee` (not a custom "liable person" DocType). The JE's debit line uses ERPNext's native `party_type = "Employee"` / `party = <employee>` mechanism so the amount appears on the standard ERPNext Employee Ledger report without extra code. Accounts (`employee_liability_account`, `discrepancy_offset_account`, `default_cash_account`) are Links to `Account`. The `Purisol Coupon Discrepancy` DocType itself is Purisol-owned because "a submittable investigation record about missing coupons" has no ERPNext primitive — it is a domain-specific concept, matching the constitution's "only when no ERPNext primitive fits" rule (written justification: the discrepancy is neither a stock movement, nor a payment, nor a journal entry; those are downstream of the decision the discrepancy encodes). |
| III | State Machine Enforcement | **PASS** | `Purisol Coupon Discrepancy` has an explicit five-state machine documented in the controller's module-level comment and enforced in `validate`: `Open → Under Review` (save-time), `Open | Under Review → Resolved - Admin Error` (submit with `resolution_action = None`), `Open | Under Review → Resolved - Delivery Man Liable` (submit with `resolution_action = Add to Liability Ledger`), `Open | Under Review → Resolved - Paid` (submit with `resolution_action = Immediate Cash Payment`). Every `Resolved - *` state is terminal — submitted docs are locked by Frappe's built-in submittable semantics; amend = 0 in permissions so no backdoor exists. Any disallowed status write raises `frappe.ValidationError`. The `Purisol Coupon Consumption Entry` state machine is untouched (no new transitions introduced in Phase 5 — Phase 4 already owns `Sold → Depleted` and `Depleted → Sold`). |
| IV | Audit Trail by Default | **PASS** | All three new DocTypes have `track_changes = 1`. The `Purisol Coupon Discrepancy` is itself a submittable — every detection is a new submitted record, every resolution is a new submit of that same record, and both events land in `tabVersion`. Detection time, discrepancy type, affected coupons, related delivery men, chosen resolution, resolved-on timestamp, and linked JE/PE name are all fields **on the discrepancy itself** (FR-019) — no state change happens as a silent field update elsewhere. The Consumption Entry's `has_warnings` flip and `discrepancies_detected` rows are the cache of "this entry caused these discrepancies"; the discrepancy records are the source of truth. |
| V | Error Handling Semantics | **PASS** | Phase 5 introduces two classes of errors, both aligned with the constitution's two-tier model: (a) **detection findings** are warning discrepancies per constitution V — they never block the Consumption Entry submit (FR-002), they create a `Purisol Coupon Discrepancy` record for human investigation, and Phase 5's whole reason-for-existing is to implement this exact pattern against Phase 4's "no warnings yet" reservation; (b) **resolution-path preconditions** (missing `liable_delivery_man`, unconfigured settings accounts) are blocking errors raised via `frappe.throw(_("..."))` — they prevent the discrepancy submit entirely, no JE/PE is partially created. Silent log-and-continue is avoided: if detection itself suffers an infrastructure failure (DB error in the service), the raise propagates out of `on_submit` and Frappe rolls the Consumption Entry transaction back — the ambiguous intermediate state is never committed. |
| VI | Role Model | **PASS** | No new role introduced. `Purisol Coupon Discrepancy` grants read/write/create/submit/cancel to `Purisol Administrator` only; System Manager gets read-only for audit. Delivery men (Employees) remain subjects, never actors — they appear as `liable_delivery_man` and in `related_delivery_men`, but hold zero system access. The resolution action of "Add to Liability Ledger" creates a JE whose `party` is the delivery-man Employee — that is an ERPNext data link, not a permission grant. |
| VII | Notification Channel | **PASS** | The "non-blocking modal dialog on Consumption Entry submit" (FR-009) is a **client-side UI surface** rendered by `frappe.msgprint`, not an ERPNext `Notification` DocType and not a `publish_realtime` event. The modal is fired synchronously from the submit-success handler on a form owned by the triggering user, so no dispatcher indirection is needed. The actual Phase-6 notification system (bell, email, WhatsApp, SMS) is explicitly out of scope for Phase 5 (spec Assumption "Out of scope: notifications"); the seam for it is "subscribe to the `Purisol Coupon Discrepancy` `after_insert` event", which Phase 6 can add as a `doc_events` hook without touching Phase 5 code. |
| VIII | Background Jobs | **PASS** | Detection per Consumption Entry submit, even in the worst-case 20-booklet full-route scenario, creates at most ~20 discrepancy documents × ~4 rows each = 80 row writes. Resolution submit creates one JE (2 rows) or one PE (1 + reference row). All well below the 100-record synchronous threshold. Zero long-running operations are introduced. A future phase that adds bulk discrepancy re-scanning (e.g. for historical data) would go via `frappe.enqueue` — the detection service is already written as a pure function over an entry, so it can be re-entered from a bulk-scan job without code changes. |
| IX | Localization | **PASS** | Every label on the three new DocTypes is wrappable by Frappe's auto-translation. Every controller error message uses `frappe._("...{0}...").format(...)` with named placeholders preserving Arabic word order. Modal text uses `__()` in JS. Select-field options (`Missing Coupons`, `Unassigned Booklet`, `Open`, `Under Review`, `Resolved - Admin Error`, `Resolved - Delivery Man Liable`, `Resolved - Paid`, `Custody Holder`, `Submitted Adjacent Coupons`, `None`, `Add to Liability Ledger`, `Immediate Cash Payment`) are stored in English in the JSON and translated via the existing `cx_purisol/translations/ar.csv` pipeline — Frappe's standard select-option translation covers this without any custom code. Print formats are not introduced in Phase 5. |
| X | Testing Discipline | **PASS** | Unit tests: three DocType test files (`test_purisol_coupon_discrepancy.py` + two child-table test files). Service tests: `api/test_discrepancy.py` with one test per helper. Integration tests: `tests/test_discrepancy_flows.py` — one test per user story (Stories 1–6) + every edge case from spec. All use `FrappeTestCase`. Phase-4 tests continue to pass unmodified (Phase 5 only widens the consumption entry controller's submit pass; existing Phase-4 assertions on "no discrepancies created" are updated to "no discrepancies created when the seeded booklet has no gap and is Sold", preserving the spirit of those assertions). A clean-database `bench run-tests --app cx_purisol` pass is the phase's definition of done. |

**Structure Decision**: Standard Frappe custom-app layout, consistent with Phases 1–4. Three new DocTypes are introduced — one submittable parent (`Purisol Coupon Discrepancy`) and two primary child tables (`Purisol Coupon Discrepancy Coupon`, `Purisol Coupon Discrepancy Related Person`). The Phase-4 stub `Purisol Coupon Discrepancy Item` is widened in place (one new Link field) rather than replaced, so no parent-table rename occurs — Phase 4's implementation has been laid out specifically to support this additive widening. Detection is a server-side service module (`api/discrepancy.py`) called from the consumption entry controller — **not** a whitelisted endpoint, so there is no external attack surface; resolution is controller-owned. Tests split by the established convention: DocType-local tests under `doctype/.../test_*.py`, service tests co-located with the service module, integration tests under `tests/test_discrepancy_flows.py`. One new patches entry anchors the phase on upgraded sites. No new role, no new custom field fixture, no new module structure.
