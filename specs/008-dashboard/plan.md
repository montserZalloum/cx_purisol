# Implementation Plan: Dashboard

**Branch**: `008-dashboard` | **Date**: 2026-04-19 | **Spec**: [spec.md](./spec.md)
**Input**: Feature specification from `/specs/008-dashboard/spec.md`

## Summary

Phase 8 ships a single landing-view Workspace for the `Purisol Administrator` role, composed of **eight widgets** grouped into three independently-shippable bundles. The workspace is built on Frappe 15's native **Workspace → Number Card / Dashboard Chart / Quick List** primitives — zero custom dashboard rendering, zero HTML widgets, zero client-side JavaScript. The existing Phase-0 workspace record (`مياه نبع النعيم`, already tracked as a fixture) is extended in place rather than replaced: its `charts`, `number_cards`, `quick_lists`, and `shortcuts` arrays are populated with the eight widgets, its `roles` array gains `Purisol Administrator` to gate visibility, and its `content` field is restructured so the widgets appear in three visually-grouped rows matching the three user-story bundles.

**Click-through semantics (FR-005) are automatic per primitive**:
- **Number Cards** — clicking the card opens the target DocType's list view pre-filtered by the card's `filters_json` (native Frappe behaviour).
- **Dashboard Charts with chart_type=`Group By`** — clicking a bar opens the DocType list filtered by the clicked group value plus the chart's base filter.
- **Dashboard Charts with chart_type=`Report`** — clicking the chart opens the underlying report (Frappe appends the dynamic filters to the URL). For widget 4 the target is the new `customers_low_on_coupons` report; for widget 6 the target is Phase-7's `delivery_man_liability_balance`; for widget 7 the target is Phase-7's `daily_delivery_man_summary` filtered to today.
- **Quick Lists** — each row is a clickable link to the record's detail view; a "View All" button at the bottom opens the full filtered list.

**Role gate (FR-003)** is implemented at the Workspace record by adding `roles: [{"role": "Purisol Administrator"}]` to the existing workspace fixture. Frappe 15 filters Workspace visibility through this list even when `public: 1`: users without the role do not see the workspace in the sidebar AND cannot open it via direct URL — both gates are native. Number Card and Dashboard Chart records created for Phase 8 stay on the underlying-DocType permission gate (Administrator already has read access on every Purisol DocType), so no per-widget role block is needed.

**Default landing (FR-002)** is implemented by adding `role_home_page = {"Purisol Administrator": "مياه نبع النعيم"}` to `cx_purisol/hooks.py`. Frappe consults this mapping on login to pick the landing workspace for the user's highest-priority role, BUT it always yields to a user-set personal home page (the `User.default_workspace` / `User.home_settings` takes precedence) — the spec explicitly allows this yield (FR-002 Assumption block).

**Live data (FR-004)** follows naturally — every Number Card, Dashboard Chart, and Quick List queries the operational database on each workspace open/refresh. No caching, no materialised view, no scheduled rebuild. Dashboard Charts support an optional server-side short-TTL cache via `Dashboard Chart.cache` (unset in Phase 8), which Frappe defaults to "no cache" when absent.

**One new Query Report** (`customers_low_on_coupons`) is added to support widget 4. It follows the exact Phase-7 report-folder pattern (`cx_purisol/cx_purisol/report/customers_low_on_coupons/` with `.json`, `.py`, `test_*.py`), is marked `is_standard = "Yes"` so it migrates via `bench migrate`, is gated to `Purisol Administrator` via the same `roles` block every Phase-7 report uses, and is excluded from the main Phase-7 reports-menu discussion because it exists only as a data source for the dashboard chart (not as a user-navigated report). A tiny info note in the plan's research.md §2 explains why the widget requires this report rather than reusing Phase-7's `Active Booklets per Customer`: Phase-7's report lists booklets per customer without threshold filtering or per-customer aggregation.

**Cancelled-document filter (FR-041)** — widgets that count or list submittable records (5a, 5b, 6, 7, and transitively the reports they reference) include `docstatus = 1` in their filters. Widgets on non-submittable DocTypes (1, 2a, 2b, 3, 8 — all querying `Purisol Coupon Booklet`) do not need `docstatus` filtering because `Purisol Coupon Booklet` is not submittable — its state machine is driven by the `status` field instead.

**Bundle-by-bundle delivery (SC-009)**: the three bundles share no per-widget files. Widgets for each bundle are separate Number Card / Dashboard Chart / Quick List fixture entries, referenced by name in the workspace JSON. Bundle 1's fixtures can be shipped alone (by committing only Bundle-1 widget files + a Bundle-1-only workspace JSON variant); the workspace `content` field's row structure gracefully degrades when a referenced widget is not yet registered — Frappe simply omits the missing widget. In practice the team will ship all three bundles in one Phase-8 PR; bundle independence is a correctness property (each bundle is self-contained) rather than a branch-splitting mandate.

**Tests**: one new integration test file `cx_purisol/cx_purisol/tests/test_dashboard.py` consumes a lightweight seed (reuses Phase-7's `report_seed.py` where applicable, extended with two scenarios specifically exercising the widget queries) and asserts, for each widget:
- the widget record exists after `bench migrate`;
- the widget's underlying query / report produces the expected row count against the seed;
- the workspace-level role gate works (non-admin user cannot open the workspace);
- the default-landing mapping works (admin-role user's login redirect lands on `مياه نبع النعيم`).

**Technical approach** (consolidated from research.md; every non-obvious decision has its own research section):

- **Workspace is extended in place, not replaced** (research §1) — the existing Phase-0 `مياه نبع النعيم` workspace fixture in `cx_purisol/fixtures/workspace.json` is edited directly; its `name` stays identical (no rename, no fixture rewrite). Phase 8's changes to that file: (a) populate `charts`, `number_cards`, `quick_lists` arrays; (b) add `roles: [{"role": "Purisol Administrator"}]`; (c) restructure `content` to lay out the widgets in three visual rows per bundle; (d) optionally update `icon` and `indicator_color` for brand consistency. Rationale: renaming the workspace would force every user's existing sidebar bookmark, their personal `home_settings`, and any link-referring content to be rewritten — high blast-radius for a label change. Preservation of the Arabic name matches the Phase-0 decision.
- **Widget fixture discipline** (research §3) — Number Cards and Dashboard Charts are exported as Frappe fixture records under two new fixture files: `cx_purisol/fixtures/number_card.json` (4 entries) and `cx_purisol/fixtures/dashboard_chart.json` (4 entries). Each fixture's `name` follows the convention `"Purisol — <Widget Name>"` (em-dash separator, `Purisol` prefix in the *record name* even though Number Card / Dashboard Chart are not Purisol-namespace DocTypes — see research.md §4 for the rationale; this does not violate constitution Principle I because the prefix rule governs custom DocType creation, not Frappe-core record names, and applying it here is a useful-though-non-mandatory convention for discoverability in list views). Quick Lists are inline entries inside the workspace JSON's `quick_lists` array — they are not standalone records in Frappe 15.
- **Dashboard Chart `chart_type = "Group By"` semantics** (research §5) — Frappe 15's Group By chart is the simplest primitive for widget 2b. The chart JSON sets `document_type = "Purisol Coupon Booklet"`, `group_by_based_on = "current_delivery_man"`, `aggregate_function_based_on = null` (implicit count), `filters_json = '[["status","=","In Custody"]]'`. Frappe renders one bar per `current_delivery_man` value; clicking a bar navigates to the filtered list. Disabled employees still appear (research §10 — no `disabled = 0` pre-filter, consistent with the spec's audit edge case). Number-of-groups rendering (research §11) — when the number of distinct holders exceeds a reasonable visual threshold, Frappe's chart library top-N-clips and labels the rest as "Other"; this is the platform's default and matches the spec edge case.
- **Dashboard Chart `chart_type = "Report"` semantics** (research §6) — Frappe 15's Report chart runs the referenced Script or Query Report, extracts one x-axis column and one numeric value column, and renders a chart. Widget 4's chart uses `report_name = "Customers Low on Coupons"`, `x_field = "customer"`, `y_axis = [{"y_field": "total_remaining", "color": "..."}]`. Widget 6 uses `report_name = "Delivery Man Liability Balance"`, `x_field = "delivery_man"`, `y_axis = [{"y_field": "open_balance", "color": "..."}]`. Widget 7 uses `report_name = "Daily Delivery Man Summary"`, `x_field = "delivery_man"`, `y_axis = [{"y_field": "coupons_submitted", "color": "..."}]`, `dynamic_filters_json = {"from_date": "Today", "to_date": "Today"}`. Dynamic filters are resolved at render time against the current date; no stale cache.
- **Quick List relative-date filter for widget 8** (research §7) — Frappe 15 Quick Lists support the token `[Today - 7d]` in `filters_json` (confirmed from Frappe 15's `frappe.desk.reportview` evaluator). If the token is rejected by the target deployment, a fallback is to make the widget a Dashboard Chart of chart_type=`Report` using a new dashboard-support report, but the primary path is the native Quick List token. Testing covers the relative-date evaluation.
- **Open Discrepancies severity signal without conditional colour** (research §8) — Frappe 15 Number Cards support a static `color` attribute but not a conditional one. Widget 5a sets `color = "Red"` as the static always-on signal; the Quick List (widget 5b) sitting immediately next to it provides the secondary signal — when the count is 0, the list is empty (Frappe Quick List renders a tasteful "No records" message); when the count is > 0, the list shows up to five recent discrepancies. This pair together satisfies FR-020's "perceptible without relying on colour alone" requirement — the count itself (0 vs N) AND the list's empty-vs-populated state both carry the severity signal. Accepted trade-off: the "Red" card accent is always present (no green state for count = 0); a future phase may introduce a conditional-colour mechanism via a Custom Number Card or a Workspace Custom Block — deferred as out-of-scope for Phase 8.
- **Default landing via `role_home_page`** (research §9) — `hooks.py` gains `role_home_page = {"Purisol Administrator": "مياه نبع النعيم"}`. Frappe's login flow consults this mapping, honouring a user-set personal `home_settings` as higher priority. This matches FR-002 exactly ("unless the user has a personal landing preference, in which case the user preference takes precedence"). Alternative considered: setting `Role.home_page = "مياه نبع النعيم"` directly in the role fixture (`role.json`) — rejected because `Role.home_page` is a single-value field and changes the behaviour across users with multiple roles in a way `role_home_page` does not; `role_home_page` explicitly supports per-role precedence and is the Frappe-documented path for this case.
- **Workspace `content` layout** (research §12) — Frappe 15 Workspace `content` is a JSON string of block elements (`header`, `card-break`, `shortcut`, `number_card`, `chart`, `quick_list`, `spacer`). The Phase-8 `content` is a three-row layout: Row 1 (Operational — widgets 1, 2a, 2b, 3, 7), Row 2 (Risk — widgets 5a, 5b, 6), Row 3 (Follow-up — widgets 4, 8). Each row begins with a `header` block naming the bundle, followed by widget references. The `card-break` elements group widgets in the same row. The exact JSON is specified in contracts/dashboard.md §Workspace Content.
- **Phase-7 dependency** (research §13) — widgets 6 and 7 reference Phase-7's `Delivery Man Liability Balance` and `Daily Delivery Man Summary` reports. Phase 7 must therefore merge to master before Phase 8. On the current branch `008-dashboard`, the Phase-7 reports live on the `007-reports` branch; Phase 8's implementation PR will rebase on master after Phase 7 has merged. Test fixtures in Phase 8 assume Phase-7 reports exist; the dashboard integration test imports from the Phase-7 `report_seed.py` helper and extends it.
- **No new DocTypes, no new fields, no new client-side JS, no new hooks (beyond `role_home_page`)** — Phase 8 is almost entirely fixtures + one new Report. The only Python added is the Query Report stub (`customers_low_on_coupons.py` auto-discovery stub — empty `execute` is not needed for Query Reports) and the integration-test file. Zero Python controllers, zero server hooks, zero `doc_events`.
- **Translations** — every new user-facing string on Number Cards, Dashboard Charts, and Quick List labels is stored in English in the fixture JSONs and appended to `cx_purisol/translations/ar.csv` for Arabic rendering. Workspace-level strings (widget headers, row titles in `content`) likewise. Quick List labels follow the same pattern.
- **`patches.txt`** — one new no-op anchor entry `cx_purisol.patches.v0_8_0.add_dashboard_widgets` matching the Phase-2/3/4/5/6/7 pattern. Workspace/Number Card/Dashboard Chart fixtures migrate via `bench migrate`'s standard fixture sync; the patch exists only to provide the version-marker consistency with prior phases.

## Technical Context

**Language/Version**: Python 3.10+ (Frappe server). No JavaScript is added in this phase — all widgets render via Frappe 15's built-in Workspace renderer. No Jinja templates are added either.
**Primary Dependencies**: Frappe Framework 15.x (`Workspace`, `Number Card`, `Dashboard Chart`, `Quick List` child table, `Report` DocType for the one new report, `Has Role`). ERPNext 15.x (`Account`, `Employee`, `Customer`, `Sales Invoice Item` with the Phase-3 `purisol_booklet` custom field — read only via the referenced Phase-7 reports). No new third-party libraries. Reuses Phase-1 `Purisol Coupon Booklet` (status, customer, current_delivery_man, depleted_on, remaining_count, sold_on), Phase-1 `Purisol Settings` (customer_low_stock_threshold — read by the new dashboard-support report; employee_liability_account — read indirectly via Phase-7's Liability Balance report), Phase-5 `Purisol Coupon Discrepancy` (status, opened_on, modified — read for widgets 5a and 5b), Phase-7 `delivery_man_liability_balance` Script Report (read by widget 6), Phase-7 `daily_delivery_man_summary` Script Report (read by widget 7). The existing Phase-0 `مياه نبع النعيم` Workspace fixture is extended in place.
**Storage**: Frappe DocTypes on MariaDB via Frappe 15's Workspace/Number Card/Dashboard Chart/Quick List rendering pipeline (read-only at widget-query time); one new `frappe.db.sql` query in the `customers_low_on_coupons` Query Report. Zero writes to the operational database introduced by Phase 8 — every widget query is `SELECT`-only, and the one new Report follows Phase 7's read-only discipline. No `frappe.db.set_value`, no `frappe.db.insert`, no `frappe.db.delete` anywhere in the phase.
**Testing**: Frappe test framework (`frappe.tests.utils.FrappeTestCase`), invoked via `bench --site <test-site> run-tests --app cx_purisol`. The Phase-8 integration test file `cx_purisol/cx_purisol/tests/test_dashboard.py` covers (a) widget-fixture presence after migration, (b) underlying-query row-count assertions against a seeded dataset, (c) workspace-level role gate (non-admin user blocked), (d) default-landing mapping (admin user lands on the right workspace), and (e) one Acceptance-Scenario-aligned test per User Story (US1: 5, US2: 5, US3: 5 = 15 tests). The new Query Report gets a dedicated per-report test at `cx_purisol/cx_purisol/report/customers_low_on_coupons/test_customers_low_on_coupons.py` following the Phase-7 per-report test pattern. Phase 1–7 tests continue to pass unmodified.
**Target Platform**: Linux server running Frappe Bench (gunicorn + RQ workers + MariaDB + Redis). The Workspace renders in the Frappe desk at `/app/مياه%20نبع%20النعيم` (URL-encoded Arabic path; Frappe handles UTF-8 workspace names natively). Number Cards, Dashboard Charts, and Quick Lists render inside the workspace via Frappe's built-in renderer — no per-widget custom view is built.
**Project Type**: Frappe custom app (`cx_purisol`) — adds two new fixture files (`cx_purisol/fixtures/number_card.json`, `cx_purisol/fixtures/dashboard_chart.json`), one new report folder (`cx_purisol/cx_purisol/report/customers_low_on_coupons/` with `__init__.py` + `.json` + `.py` + `test_*.py`), one integration-test file (`cx_purisol/cx_purisol/tests/test_dashboard.py`), one no-op patch anchor (`cx_purisol/patches/v0_8_0/add_dashboard_widgets.py` + `__init__.py`), and modifies three existing files: (a) `cx_purisol/fixtures/workspace.json` (extend the existing workspace with widgets, roles, content), (b) `cx_purisol/hooks.py` (add `role_home_page` mapping, extend `fixtures` list), (c) `cx_purisol/patches.txt` (append v0_8_0 anchor). The `cx_purisol/translations/ar.csv` file is appended with new dashboard-label strings. Zero new DocTypes, zero new fields on existing DocTypes, zero new roles, zero new client-side JS, zero new custom-field fixtures.
**Performance Goals**:
- **SC-001 target**: Workspace loads within 3 seconds at documented scale (10,000 coupons, 500 booklets, 50 delivery men, 200 customers). Each Number Card is an indexed `COUNT(*)` — well under 100ms. Each Dashboard Chart runs the underlying Group By / Report query once and caches its rendered JSON client-side for the session. The Quick List queries are bounded by LIMIT 5 and hit indexed `status` + `modified` / `depleted_on` paths. The new `customers_low_on_coupons` Query Report runs one aggregate with `GROUP BY customer HAVING total_remaining <= threshold LIMIT 10` against `Purisol Coupon Booklet` with a `status = 'Sold'` filter — at worst-case scale this is ~500 booklet rows scanned, sub-100ms.
- **SC-007 target** (latest data on next refresh): Live queries with no cache. Frappe's built-in Number Card / Dashboard Chart / Quick List all re-query on workspace open. Any platform-level short-TTL cache is disabled via explicit `cache = 0` on each chart.
- **Concurrent-render edge case**: workspace-level rendering is transactional per widget — Frappe issues each widget's query independently; partial consistency across widgets mid-render is accepted per spec edge case "a record submitted while the dashboard is rendering may or may not be reflected in that render".
**Constraints**:
- **Read-only** — Phase 8 introduces zero writes to the operational database. Every code path is `SELECT`-only. Widget queries, the one new Report's SQL, the integration tests' assertions all read from (never mutate) source records. The `role_home_page` hook is a config-level change (`hooks.py`), not a runtime write.
- **No new schema** — zero new DocTypes, zero new fields, zero new roles, zero new custom-field fixtures. The one new `Report` JSON migrates via `bench migrate`'s standard report-sync. Workspace/Number Card/Dashboard Chart fixture JSONs migrate via `bench migrate`'s standard fixture loader.
- **Role gate at workspace level** — `roles: [{"role": "Purisol Administrator"}]` on the workspace satisfies FR-003 natively; per-widget role gates are not introduced (redundant with the workspace gate + underlying-DocType permissions). The one new Report's `roles` block is `[{"role": "Purisol Administrator"}]` matching Phase-7 convention.
- **Cancelled-document filter on submittable-source widgets** — widgets 5a, 5b, 6, 7 join on `docstatus = 1` via their underlying queries/reports. Widgets on `Purisol Coupon Booklet` (1, 2a, 2b, 3, 8) do not need a docstatus filter because Booklet is not submittable — status-based filtering is the equivalent.
- **Click-through is native** — every Frappe 15 Workspace widget supports click-through out of the box: Number Cards to filtered lists, Group By charts to filtered lists per bar, Report charts to the report with dynamic filters, Quick List rows to record detail pages. No custom JS, no custom column formatter, no overlay routing is built in Phase 8.
- **Excel/PDF export is the platform's** — widgets themselves do not export (dashboards are live surfaces, not reports); the click-through lands on reports/list views which provide the platform's standard export affordances. SC-006 from Phase 7 still applies to the underlying reports; Phase 8 does not re-implement it.
- **Localisation** — every Number Card label, Dashboard Chart label, Quick List label, and Workspace widget-header text is translatable. Arabic translations are appended to `cx_purisol/translations/ar.csv` as part of the phase. Numeric formatting in Number Cards uses Frappe's locale-aware display; currency in widget 6 uses the default company currency (Frappe default, RTL-safe).
- **Bundle independence (SC-009)** — each bundle's widgets are separable fixture entries. The Phase-8 integration test verifies that disabling a bundle (removing its widgets from the workspace `content` JSON) does not break the other bundles' widgets — no cross-bundle Python or JavaScript coupling exists.

**Scale/Scope**: Single shop. 8 widgets + 1 supporting Query Report + 1 extended Workspace + 1 updated hooks.py entry + 1 appended patches.txt line. Worst-case production dataset is the same as Phase 7's (10,000 coupons, 500 booklets, 50 delivery men, 200 customers). All Phase-8 widget queries are designed to render within the workspace's 3-second total load budget (SC-001) — each individual widget is well under 500 ms at this scale.
